## Why

Во многих случаях работа начинается не с чистого листа, а с уже существующей внешней системы: чужого кабинета, внутреннего сервиса, legacy-продукта, partner UI или текущего интерфейса клиента. Для пользователя проблема не в том, чтобы придумать новый экран с нуля, а в том, чтобы сначала втянуть существующий интерфейс в рабочий контур и уже потом думать, как его переделывать.

На старте проекта desengine должен уметь работать с таким входом:

- взять внешний интерфейс как исходный материал;
- превратить его во внутренний проектовый контекст;
- дать возможность дальше рассматривать, разбирать и перерабатывать его уже внутри системы.

Без этого продукт остаётся сильнее заточен под greenfield-сценарий, чем под реальную практику проектной работы.

## What Changes

- Создаётся idea-change `idea-system-upload` под `focus-product`.
- Идея фиксирует продуктовую гипотезу:
  - на старте проекта пользователь может «засосать» в систему интерфейс внешней системы;
  - этот интерфейс становится материалом для дальнейшей проработки внутри desengine;
  - ценность состоит не только в импорте как таковом, а в переходе от внешнего UI к внутреннему рабочему контексту проекта.
- Change удерживает вместе три аспекта одной идеи:
  - вход внешнего интерфейса в проект;
  - преобразование внешнего материала в понятный внутренний контекст;
  - дальнейшую проработку этого материала как проектового объекта, а не как одноразового вложения.

## Non-goals

- Не выбирать сейчас конкретный транспорт входа: URL, набор скриншотов, запись экрана, HTML snapshot, design export или другой формат.
- Не обещать в этом change точную визуальную реконструкцию, editable DOM или production-grade reverse engineering.
- Не переходить в реализацию ingest pipeline, parser layer, browser automation или storage-модели.

## Impact

- В product-контуре появляется отдельная идея про старт проекта из существующего интерфейса, а не только из пустого проекта или ручного набора артефактов.
- Будущие changes смогут обсуждать ingestion, обзор, decomposition и redesign external UI как одну связанную тему.
- Traceability для последующих behavior-change changes можно будет строить вокруг сценария «внешняя система стала исходным проектовым материалом».

## Acceptance Criteria

- В OpenSpec есть отдельный idea-change, который описывает старт проекта через загрузку интерфейса внешней системы.
- В одном месте зафиксированы ключевые требования идеи:
  - внешний интерфейс становится входом в проект;
  - после загрузки с ним можно работать как с внутренним материалом системы;
  - идея нацелена на последующую проработку, а не только на архивирование чужого UI.
- Для downstream changes перечислены главные вопросы:
  - какой минимальный тип входа нужен первым;
  - что именно считается «интерфейсом системы» для загрузки;
  - в каком виде этот материал становится проектовым объектом внутри desengine;
  - как пользователь переходит от загруженного интерфейса к дальнейшей проработке.
- Сохранён понятный тестовый и traceability-план для будущих behavior-change changes.

## Тестовая часть change

- Затронутые OpenSpec capability/scenarios:
  - capability: `projects`
  - capability: `workflow`
  - scenario: idea-change фиксирует старт проекта через загрузку интерфейса внешней системы для дальнейшей проработки.
- Уровень проверки: `static/contract` (валидация OpenSpec-артефактов).
- Команда запуска: `npm run test:traceability`.
- Mock/fixture-данные: не требуются.
- Live credentials: не требуются.
