## Context

Для многих проектных сценариев отправной точкой является уже существующая внешняя система. Человеку важно не просто посмотреть на неё, а перенести её интерфейс в рабочее пространство, где можно:

- удерживать его в фокусе;
- разбирать на части;
- обсуждать изменения;
- развивать новый проект на основе уже существующего интерфейса.

Если такой вход отсутствует, продукту сложнее быть инструментом реальной проектной трансформации: он видит только новые сущности, но не умеет начать работу с уже существующего системного интерфейса.

## Goals

- Зафиксировать идею старта проекта через ingest внешнего интерфейса.
- Подчеркнуть, что ценность не в загрузке как в архивировании, а в дальнейшей проработке.
- Подготовить рамку для будущих product/discovery changes без перехода в delivery и implementation.

## Non-goals

- Не определять сейчас единый канонический формат загрузки.
- Не обещать автоматическое превращение загруженного интерфейса в готовый код или готовую дизайн-систему.
- Не превращать этот idea-change в parser/adapter implementation plan.

## Decisions

### 1. System upload рассматривается как старт project flow

Идея не про вложение файлов ради хранения. Она про старт проекта:

- пользователь приходит с внешней системой;
- загружает её интерфейс;
- получает внутренний материал для дальнейшей работы.

### 2. Единицей ценности является не upload сам по себе, а дальнейшая проработка

Важно не просто принять внешний интерфейс в систему, а сделать его:

- обозримым;
- пригодным для фокусировки;
- пригодным для обсуждения и развития;
- связанным с последующими проектовыми действиями.

### 3. Формат входа пока остаётся открытым

На стадии идеи полезно сохранить свободу:

- это может быть статический снимок интерфейса;
- может быть пакет экранов;
- может быть структурный экспорт;
- может быть другой тип ingest из внешней системы.

Рано фиксировать конкретный transport, пока не определена минимальная пользовательская ценность.

### 4. Greenfield и legacy-first должны сосуществовать

desengine не должен быть только инструментом создания нового интерфейса. Он должен уметь принимать уже существующий внешний интерфейс как исходный объект проектной работы.

## Risks

- Если идея будет сведена только к загрузке скриншотов, она не даст рабочего перехода к проектовой проработке.
- Если слишком рано зафиксировать технический способ ingest, продукт может выбрать неудобный вход и потерять широту сценариев.
- Если не удерживать связь с дальнейшей проработкой, system upload превратится в склад внешних материалов, а не в старт project flow.

## Trade-offs

- Открытый формат входа оставляет больше пространства для discovery, но отодвигает конкретику реализации.
- Сильный фокус на старт проекта из внешней системы делает идею более полезной для реальных сценариев, но требует сложнее продумывать переход к внутреннему workflow.

## Open Questions

- Какой минимальный формат входа даёт первую полезную версию идеи:
  - один экран;
  - несколько экранов;
  - структурный snapshot системы;
  - комбинированный ingest?
- Что пользователь должен получить сразу после загрузки:
  - обзор интерфейса;
  - проектовую карту экранов;
  - пространство для annotations и decomposition;
  - другой тип рабочего контекста?
- Где проходит граница между «засосать интерфейс» и «понять систему настолько, чтобы начать её redesign»?

## Testing

- Для самого idea-change:
  - `static/contract` на traceability OpenSpec-артефактов;
  - команда: `npm run test:traceability`.
- Для downstream behavior-change:
  - unit/contract на ingest model и представление загруженного интерфейса;
  - component/browser на старт project flow из внешней системы;
  - integration или e2e smoke на сценарий загрузки интерфейса и перехода к дальнейшей проработке.
