## Контекст

Родительская workbench-линия уже заявляет верстак как важную рабочую поверхность, но унаследованные формулировки всё ещё тащат устаревшую служебную лексику и привязку к прежнему runtime-пути.

Текущий продуктовый фокус другой:

- пользователь работает над проектом;
- workflow принадлежит проекту;
- subject работы может быть проектом, компонентом или другой project-scoped сущностью;
- верстак должен быть прощупываемым до того, как ему разрешат стать местом реальной работы.

Из этого следует, что первый честный шаг сейчас не в богатой tool-модели и не в классификаторе верстаков, а в materialized shell, который уже:

- виден в пользовательской структуре;
- имеет понятные связи с проектом и workflow;
- не притворяется готовым рабочим местом.

## Решение

### 1. Вводится generic workbench capability без типологии

Активный capability `workbench` описывает не семейство специализированных верстаков, а одну базовую форму:

- `WorkbenchDefinition` как описание shell-поверхности;
- `WorkbenchSession` как конкретную materialized-сессию внутри проекта.

На этом этапе система не классифицирует верстаки по видам. Это сознательное ограничение, чтобы не зацементировать слишком раннюю taxonomy.

### 2. WorkbenchSession принадлежит проекту, workflow и subject

Минимальная модель сессии должна выражать три привязки:

- `projectId` как canonical owner;
- `workflow` как источник направляющего контекста;
- `subject` как указание, над чем именно строится shell.

Минимальный shape контракта:

- `id`
- `definitionId`
- `projectId`
- `workflowDefinitionId` или другой устойчивый workflow reference
- `subject`
- `status`
- `lockedReason`
- `createdAt`
- `updatedAt`

Здесь важно не точное техническое имя полей, а продуктовый смысл:

- workbench не живёт сам по себе;
- workbench не является дочерней заменой проекта;
- workbench не вводит скрытую промежуточную пользовательскую сущность.

### 3. Единственный режим первой волны: locked shell

Открываемая пользователю поверхность должна быть честно ограничена:

- shell можно увидеть и открыть;
- по нему можно понять, к какому проекту, workflow и subject он относится;
- shell объясняет, что рабочий режим ещё не включён;
- запуск реальной работы, редактирование, tool manipulation и выпуск результатов недоступны.

Это нужно, чтобы materialization не создавала ложного обещания готового редактора.

### 4. Project surface публикует workbench как часть проектной работы

Страница проекта должна уметь:

- показывать, что у проекта есть materialized workbench shell;
- объяснять, с каким subject он связан;
- давать переход в locked route этого shell.

При этом project page остаётся главной рабочей поверхностью. Workbench пока не конкурирует с ней и не уводит пользователя в другой продуктовый контур.

### 5. Workflow публикует workbench binding, а не отдельную рабочую вселенную

Workflow должен уметь материализовать workbench shell как downstream surface:

- shell наследует project context;
- shell наследует workflow context;
- shell использует тот же `subject`, который уже удерживает workflow.

Такой binding делает Workbench архитектурно полезным:

- это не просто новый route;
- это внешне наблюдаемое продолжение project-owned workflow.

### 6. Что сознательно не решается сейчас

Этот change не фиксирует:

- типы верстаков;
- полноценный workbench registry инструментов;
- допуск к реальной работе на верстаке;
- rich layout/panel composition beyond shell-level contract;
- migration всех старых UI-поверхностей к новой модели.

Эти темы должны вернуться позже, когда materialized shell уже будет наблюдаем в продукте и понятен как сущность.
