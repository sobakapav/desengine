## Why

Мы уже фиксируем направление про workflow на уровне задачи. Но у проекта тоже должна быть аналогичная сущность: план/roadmap, который:

- задаёт структуру работы над проектом (этапы, цели, вехи);
- связывает задачи между собой;
- хранит «намерение» проекта (что и зачем делаем);
- помогает управлять настройками и данными проекта по этапам.

Сейчас это только идея, требующая проработки. Нужно исследование и план, чтобы не потерять направление и не зафиксировать преждевременно неверный формат.

## Зависимости

Этот change зависит от `dev-mode-project-work-2026-05-19`, потому что roadmap должен быть project-scoped и опираться на сущность проекта как контейнер данных/настроек.

## What Changes

Этот change — исследовательский/плановый. Результаты:

- определение сущности **Project Roadmap** (или Project Plan) и её жизненного цикла;
- типы элементов roadmap:
  - вехи/эпики/этапы;
  - связи с задачами (Task refs);
  - критерии готовности (acceptance);
  - зависимость/порядок.
- связь Roadmap ↔ Task Workflow:
  - как roadmap влияет на выбор/шаблоны workflow задач;
  - как прогресс задач отражается в прогрессе roadmap.
- MVP UX: как пользователь видит roadmap и управляет им.
- план внедрения поэтапно (будущие changes) + тестовый план/traceability.

## Non-goals

- Реализация полноценного планировщика/PM-системы.
- Автоматическое построение roadmap «из воздуха» (на первом шаге).
- Командный режим (позже).

## Capabilities

### New Capabilities
- `project-roadmap`: план/roadmap проекта.

### Modified Capabilities
- `projects`: проект получает управляемый план.
- `workflow`: workflow задач может быть связан с этапами roadmap.

## Acceptance Criteria

- Описан контракт roadmap (структура, связи, статусы).
- Описаны сценарии: создать план, добавить вехи, привязать задачи, видеть прогресс.
- Описан план внедрения в виде будущих changes + тестовый след.
