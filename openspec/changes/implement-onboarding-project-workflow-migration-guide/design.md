## Context

В onboarding-линии нужно не просто переименовать старые уровни, а реально объяснить owner'у контента,
как собрать новую задачу в проектном и workflow режиме. Ему нужно понимать:

- какая сущность теперь считается точкой входа;
- как раскладывать задачу на workflow-этапы;
- какие metadata нужны для UI, prompts, проверки и результата;
- какие поля должны исчезнуть из старой level-центричной схемы.

Без такой инструкции downstream UI-волны начнут угадывать структуру onboarding-задач по ходу работы.

## Goals / Non-Goals

**Goals:**

- Дать content-owner'у пошаговую и практическую инструкцию, как мигрировать onboarding-задачи.
- Зафиксировать mapping старых task/level сущностей на проектный, workflow и result-aware режим.
- Явно описать metadata-поля, их место хранения и минимальные примеры заполнения.

**Non-Goals:**

- Не менять код onboarding UI в этом change.
- Не переписывать все существующие onboarding-задачи прямо сейчас.
- Не проектировать заново общие contracts `projects`, `workflow` или `workbench`.

## Decisions

1. Инструкция должна быть ориентирована на контент-менеджера, а не на разработчика.
   Поэтому в ней нужен язык задач, шагов, проверки и результата, а не только внутренние имена runtime-модулей.

2. Инструкция должна содержать явную mapping-таблицу:
   - старое поле / старая сущность;
   - новое поле / новая сущность;
   - где это теперь хранится;
   - зачем это нужно UI и workflow.

3. Metadata нужно разделить минимум на три группы:
   - project-aware контекст задачи;
   - workflow-структура и шаги;
   - проверка/результат и их пользовательские статусы.

4. Инструкция должна завершаться коротким checklist'ом готовности, чтобы по ней можно было принять миграцию конкретной onboarding-задачи.

## Risks / Trade-offs

- [Risk] Инструкция скатится в архитектурную заметку и не поможет человеку, который реально правит onboarding content.
  -> Mitigation: требовать конкретные поля, примеры и готовый migration checklist.

- [Risk] Инструкция окажется слишком жёсткой и заблокирует future onboarding slices.
  -> Mitigation: фиксировать только обязательный минимум для пути `проект -> workflow -> проверка/чеклист -> результат`.
