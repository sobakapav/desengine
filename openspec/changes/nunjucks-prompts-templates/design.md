## Дизайн: Nunjucks как слой рендера промптов

### 1) Цели рендера

- Компоновать промпты через `include`/partials и (опционально) `extends`/`block`.
- Передавать строго определённый контекст (user/task/level/runtime) в шаблон.
- Обеспечить режим совместимости: текущие `.md` без Nunjucks-конструкций отдаются как есть.

### 2) Предлагаемая архитектура (высокоуровнево)

- `PromptTemplateLoader`:
  - умеет читать шаблоны из `appConfig.promptsRoot` и `appConfig.onboardingPromptsRoot`;
  - поддерживает иерархию `levels/<levelId>/*.md`;
  - предусматривает кэш (prod) и управляемое отключение/сброс (dev).

- `PromptRenderContext` (строго типизированный объект):
  - `user`: настройки пользователя, влияющие на промпт (например, `designSystemId`);
  - `task`: агрегированные данные задачи (например, `allowedFiles`, `images`, `currentFilesSummary`);
  - `level`: `{ id, number }` + прочие метаданные (если нужны).

- `renderPrompt(kind, name, context)`:
  - возвращает итоговый текст промпта;
  - при отсутствии/пустом `context` должен совпадать с текущим поведением.

### 3) Формат и структура шаблонов
Фиксируем формат: **переходим на `.njk`** для всех промптов, которые рендерятся системой.

### 4) Компонование (пример на уровне идеи)

- `prompts/partials/common-rules.njk` — общие правила поведения.
- `prompts/partials/ds/{{ user.designSystemId }}.njk` — правила активной дизайн-системы.
- `prompts/start-component.njk` — собирает итог:
  - include common-rules
  - include ds rules
  - include task-specific blocks (allowed files, images, текущий контекст)

Также фиксируем поддержку наследования: базовый layout-шаблон (`base.njk`) + `extends`/`block` для сценариев start/iterate/check.

### 5) Ограничения и безопасность

- Шаблоны должны быть «данные + композиция», без скрытых побочных эффектов.
- Фильтры/глобалы — только из белого списка (если понадобятся).
- Автоэскейпинг: для markdown/plaintext обычно выключен, но важно явно зафиксировать.

### 6) Совместимость и миграция

Этапы:

1) Ввести Nunjucks-рендер и начать миграцию расширений `.md → .njk` без изменения контента.
2) Добавить тесты, подтверждающие идентичность output (snapshot/строковое сравнение).
3) Начать выносить повторяющиеся части в partials и подключать их из шаблонов.

### 7) Деградация при ошибках рендера (первый этап)

Фиксируем стратегию на старте: **деградация вместо hard-fail**.

Ожидаемая логика (точно уточнить в реализации):
- если шаблон не найден или не удалось отрендерить — возвращаем «упрощённый» текст (например, raw-файл, если он есть) и логируем причину;
- если это критичный промпт (например, level start) — возвращаем fallback + показываем явное предупреждение в логах/диагностике.
