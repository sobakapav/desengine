## Why

OpenSpec в проекте уже работает не только как внешний формат хранения specs и changes. Он стал внутренним слоем управления изменениями: задаёт структуру contract-first работы, роли changes, передачу контекста между чатами и связь между продуктовым контрактом, тестами и кодом.

Использование OpenSpec только как “кастомной metadata-схемы” уже слишком узко. Кастомизация схемы остаётся важной, но это лишь один из потоков в более широком OpenSpec-слое проекта.

Нужно:

- выделить OpenSpec-слой как отдельный продуктовый и инструментальный контур;
- продолжить развитие кастомной схемы как одного из направлений этого контура;
- развивать workflow changes в целом: dispatcher/release orchestration, handoff, preflight, traceability, закрытие changes;
- обеспечить, чтобы инструменты вокруг OpenSpec поддерживали не только metadata, но и жизненный цикл передачи работы.

Этот dispatcher становится тактическим контейнером для всего OpenSpec-слоя проекта.

## What Changes

Этот change — тактический dispatcher для OpenSpec-слоя. Результат:

- OpenSpec-слой описан как совокупность:
  - продуктового контракта;
  - workflow changes;
  - внутреннего инструментария;
- кастомная схема change развивается как отдельное направление внутри этого слоя:
  - формализация существующих кастомных полей (начиная с `short`);
  - развитие metadata-контракта;
  - правила совместимости и миграции;
- workflow changes развивается как отдельное направление:
  - dispatcher/release/implement/fix механика;
  - handoff между change-ами и чатами;
  - preflight и gate готовности;
  - каскад закрытия и traceability;
  - стратегическое владение roadmap и их наследование в dispatcher-контур;
- сохраняется и расширяется трёхслойная модель истины:
  - OpenSpec = продуктовый контракт (`что и зачем`);
  - GitHub Issues = временные технические постановки (`как делаем сейчас`);
  - код = фактически реализованное поведение (`что реально создано`);
- набор product-oriented полей и workflow-правил стабилизируется и расширяется, например:
  - классификация change по механике управления продуктом: `focus`, `idea`, `producer`, `dispatcher`, `implement`;
  - статус/этап исполнения;
  - зависимости (в явном виде, если принимаем такой механизм);
  - owner/контакт;
  - affected capabilities/scenarios (как минимум ссылками);
  - тестовый уровень и команды проверки (как минимум ссылками/полями).
  - связь с реализацией: `issue` (ссылка на главный GitHub issue при старте техпроработки), `review_sync_state` (none/needs-sync/needs-review/in-sync).
  - иерархия управления: `parent_change`, `strategy_root`, `roadmap_ref`/`roadmap_refs`, `release_ref`, `producer_ref`, `execution_mode`.
  - для implement: `verification_level` и `verification_command`;
  - для handoff: отдельный исполнительский контекст, достаточный для передачи работы.
- обновление/план обновления внутренних инструментов под OpenSpec-слой:
  - создание change (`openspec:new`);
  - диспетчеризация и preflight (`os:begin`, `os:dispatch`, `os:req`, `os:ctx`, `os:close`, `os:rename`);
  - листинги active/release changes, где `npm run os` становится основным tree-view;
  - проверки traceability/тестового слоя;
  - контекстная передача между changes.

## Non-goals

- Изменение install-critical инфраструктуры ради OpenSpec-слоя.
- «Большой взрыв» миграции всех changes за один раз без поэтапного плана.
- Попытка в одном dispatcher закрыть все будущие направления эволюции OpenSpec без отдельной декомпозиции в child changes.

## Capabilities

### Modified Capabilities
- `admin-tools`: внутренний OpenSpec-инструментарий и workflow changes образуют отдельный OpenSpec-слой проекта.

## Acceptance Criteria

- Есть документированное описание OpenSpec-слоя проекта: его направлений, границ и уже принятых workflow-инвариантов.
- Кастомная схема metadata зафиксирована как одно из направлений OpenSpec-слоя, а не как весь слой целиком.
- `short` и другие выбранные поля формализованы и поддержаны инструментами (минимум: не ломают листинг/создание).
- Для `short` в режиме `short_policy: strict-v1` действует валидационный контракт (маленькая буква в начале, максимум 75 символов, без пунктуации в конце), и нарушение ловится статической проверкой.
- Для product-only change допускается отсутствие `issue`; связь с issue становится обязательной только после явного старта технической проработки change.
- Процесс закрытия change включает проверку трёх слоёв: продуктовый контракт, технические issue и фактический код/тесты.
- Валидатор схемы контролирует роли `focus/release/idea/producer/dispatcher/implement/fix` и допустимые связи между ними.
- Стратегический уровень допускает верхнеуровневые changes типов `focus`, `idea`, `producer`; `dispatcher` как тактический change обязан иметь родителя.
- Release-поток работает как delivery-диспетчер: формирует состав поставки через `release_ref`, не ломая тактическое подчинение implement/fix через `parent_change`.
- Child changes получают отдельный handoff-контур и не считаются готовыми к исполнению без содержательной передачи контекста.
- Есть план миграции существующих changes (поэтапно) и правила совместимости.

## Impact

- Стратегические changes (`focus`, `idea`, `producer`) становятся владельцами roadmap-документов и обязаны поддерживать их как рабочий контекст для downstream dispatcher.
- `producer`-change ведёт собственный roadmap и не получает direct implement/fix исполнителей: он согласует ожидания с downstream dispatcher changes, а возникающие конфликты ожиданий между producer и dispatcher считаются полезным управленческим сигналом, а не ошибкой модели.
- Producer работает с dispatcher через переговорный контекст, но не через прямое `parent_change`.
- Dispatcher перестаёт хранить локальные roadmap как источник истины и вместо этого явно ссылается на roadmap стратегических владельцев.
- Producer-контекст становится отдельной metadata-меткой `producer_ref` только для implement/fix: dispatcher не хранит её у себя и остаётся тактически независимым.
- Tooling и traceability начинают проверять не только наличие roadmap, но и корректность их наследования.
