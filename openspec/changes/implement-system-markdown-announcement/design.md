## Контекст

- `app/page.tsx` и `app/system/page.tsx` используют `SystemScreen` как пользовательскую системную поверхность.
- `SystemScreen` сейчас рендерит навигацию и диагностические карточки ресурсов, но не содержит отдельного управляемого блока продуктового анонса.
- В проекте уже есть `MarkdownContent`, который умеет безопасно рендерить Markdown, включая ссылки, картинки и Mermaid.
- Конфигурация server-side источников и путей уже проходит через `lib/system/config/server.ts`, поэтому внешний URL анонса логично задавать тем же контуром.

## Решение

- Рассматривать анонс как пользовательский UI-блок системной страницы, а не как новый системный ресурс диагностики.
- Источник Markdown-анонса должен задаваться конфигурацией, чтобы адрес внешнего сайта можно было менять без правки пользовательского интерфейса.
- При реализации отдельно определить:
  - где и как выполняется fetch внешнего Markdown;
  - какой timeout, кэширование или graceful fallback допустимы для системной страницы;
  - что видит пользователь, если источник недоступен, вернул пустой ответ или сломанный контент.
- Для отрисовки использовать существующий `MarkdownContent`, а не вводить второй Markdown-renderer.

## Ограничения и риски

- Внешний источник не должен превращать загрузку системной страницы в хрупкую live-зависимость без понятного fallback.
- Нужно не смешать анонс с ресурсной диагностикой: анонс сообщает продуктовую новость, а не состояние системы.
- Если change меняет наблюдаемый контракт top-level system entry, потребуется синхронно обновить соответствующий OpenSpec-контракт в `openspec/specs/**`.
