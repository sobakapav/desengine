## Context

Сейчас в активном продукте пересекаются три темы:

- проект как контейнер пользовательской работы;
- задача и workflow как операционная единица;
- roadmap проекта как потенциальный слой координации задач, этапов и прогресса.

Раньше эти направления были разведены по двум producer-линиям. Для текущей стадии это оказалось преждевременно: до delivery ещё рано, а продуктовую гипотезу полезнее удерживать в одном idea-change.

## Goals

- Зафиксировать `Project Workspace` как базовую рамку будущего project mode.
- Зафиксировать, что `Task` и `Workflow` должны стать project-scoped сущностями.
- Определить MVP-first порядок движения:
  - сначала проект, project-scoped данные и task/workflow binding;
  - потом roadmap проекта как отдельное расширение.
- Подготовить основу для последующих producer/dispatcher changes без преждевременной детализации runtime.

## Non-goals

- Не определять окончательный runtime-контракт storage и синхронизации.
- Не обещать roadmap проекта в первом delivery-срезе.
- Не фиксировать полную навигационную и информационную архитектуру project mode.
- Не превращать этот change в producer или implement-контур.

## Decisions

### 1. Project mode рассматривается как единая продуктовая тема

`idea-project-mode` удерживает общий контур:

- `Project Workspace` и project-scoped данные;
- `Task` / `Workflow` внутри проекта;
- потенциальный `Project Roadmap`, связанный с задачами и прогрессом.

### 2. MVP начинается не с roadmap, а с project scope

Первая волна должна закрыть минимальный project mode:

- у пользователя есть выбранный активный проект;
- у проекта есть собственные настройки и данные;
- задачи, workflow и связанные артефакты начинают жить внутри проекта.

Roadmap проекта сознательно выносится в следующую волну после стабилизации этой базы.

### 3. Roadmap остаётся частью стратегического контура, но не первой delivery-целью

Идея roadmap не удаляется из change. Она сохраняется как следующий уровень развития project mode:

- этапы и вехи проекта;
- связь roadmap items с задачами;
- отображение прогресса проекта через прогресс задач.

## Risks

- Если граница MVP окажется размытой, downstream changes снова смешают project scope и roadmap в один delivery-срез.
- Если project-scoped модель будет определена слишком слабо, разные подсистемы начнут вводить несовместимые project boundaries.
- Если roadmap начать слишком рано, можно перегрузить первый срез координационным UX вместо стабилизации базовой модели проекта.

## Trade-offs

- Единый idea-change снижает фрагментацию продуктовой гипотезы, но требует аккуратной декомпозиции на следующем уровне.
- MVP-first подход замедляет обсуждение roadmap-функций, зато уменьшает риск преждевременного усложнения.
- Отложенный roadmap делает первый срез уже, но даёт более чистую опору для последующей project-level координации.

## Open Questions

- Какой минимальный `Project` нужен, чтобы не ломать текущие сценарии?
- Какие данные должны стать project-scoped в первую очередь:
  - UI kit и режим UI;
  - задачи и их история;
  - артефакты;
  - workflow instances?
- Какой минимальный UX нужен пользователю в MVP:
  - просто выбрать активный проект;
  - видеть project-scoped список задач;
  - управлять project settings без roadmap-слоя?
- В какой момент после MVP roadmap становится оправданной следующей волной?

## Testing

- Для самого idea-change:
  - `static/contract` на traceability OpenSpec-артефактов;
  - команда: `npm run test:traceability`.
- Для downstream behavior-change:
  - unit/contract на модель `Project`, `Task`, `Workflow`, а позже `ProjectRoadmap`;
  - component/browser или e2e smoke на выбор проекта, изоляцию project-scoped данных и базовый progress UX.
