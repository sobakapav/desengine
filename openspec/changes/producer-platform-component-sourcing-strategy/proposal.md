## Why

desengine уже использует ряд сильных готовых решений из React-экосистемы, но проекту нужен отдельный продюсерский контур, который системно отвечает на более общий вопрос: какие стандартные, зрелые и хорошо оттестированные React-модули и компоненты стоит использовать по умолчанию, чтобы не писать generic UI/runtime primitives вручную без необходимости.

Без такого исследования команда рискует впадать в две крайности:
- переписывать вручную то, что в экосистеме уже давно стандартизовано и стабильно;
- либо подключать зависимости ситуативно, без понятных критериев зрелости, совместимости и ownership.

## What Changes

Этот change становится продюсерским и фиксирует:

- общую стратегию максимизации использования готовых хорошо оттестированных модулей и компонентов в React-экосистеме;
- критерии, по которым desengine должен предпочитать готовый ecosystem-standard primitive вместо самописного;
- правила первичной оценки кандидатов: зрелость, распространённость, поддерживаемость, совместимость с React/Next, качество документации и тестовый след;
- направления будущих producer/dispatcher/implement changes, если проекту понадобится расширять конкретные зоны UI/runtime.

## Non-goals

- Этот change не занимается деталями уже внедрённых модулей и не ревизует их поштучно.
- Этот change не добавляет новые runtime dependencies сам по себе.
- Этот change не навязывает reuse как догму: если готовый модуль ломает локальные ограничения, допустим собственный слой.
- Не меняем install-critical стек.

## Acceptance Criteria

- Есть продюсерская рамка, объясняющая, зачем desengine максимизирует использование готовых React-primitive решений.
- Есть критерии отбора ecosystem-standard модулей и условия отказа от них.
- Зафиксированы направления follow-up changes для конкретных подсистем, не разбирая уже внедрённые модули поштучно.
