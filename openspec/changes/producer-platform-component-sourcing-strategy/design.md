## Scope

Исследование покрывает общий подход desengine к выбору готовых React-модулей и компонентов:

- как распознавать ecosystem-standard primitive;
- в каких зонах готовое решение должно быть default-поиском;
- по каким признакам модуль считается достаточно зрелым для рассмотрения;
- когда проект обязан отказаться от самописной реализации generic UI/runtime задачи;
- в каких случаях, наоборот, собственный слой остаётся правильным решением.

Этот change не уходит в аудит уже внедрённых модулей и не ведёт поштучный реестр текущих зависимостей.

## Research Questions

1. Какие классы задач в desengine по умолчанию должны решаться через готовые React-экосистемные primitives, а не через собственную реализацию?
2. Какие критерии зрелости и стандартности обязательны для кандидата:
   - устойчивое использование в экосистеме;
   - понятная документация;
   - активная поддержка;
   - совместимость с актуальным React/Next-стеком;
   - прозрачный тестовый и migration story.
3. Какие стоп-факторы должны вести к отказу от готового модуля:
   - локальные privacy/local-first ограничения;
   - нежелательная смена install-critical стека;
   - vendor lock-in без boundary;
   - непрозрачная деградация или слабая эксплуатационная предсказуемость.

## Decision Frame

Базовый порядок рассуждения для follow-up changes:

1. Сначала искать готовый ecosystem-standard primitive.
2. Потом проверять его на зрелость, эксплуатационный риск и совместимость со стеком.
3. Затем выбирать форму интеграции:
   - `reuse`, если модуль можно использовать почти напрямую;
   - `adapt`, если нужен boundary;
   - `build`, если generic библиотека не проходит ограничения проекта.

## Deliverables

- Исследовательская рамка выбора готовых React-модулей и компонентов.
- Список критериев отбора и стоп-факторов.
- Список направлений, где для desengine особенно важно сначала искать стандартный внешний primitive.
- Рекомендации по тому, какие future producer/dispatcher changes нужны дальше.

## Risks / Trade-offs

- [Риск] Исследование скатится в каталог уже подключённых библиотек.
  → Mitigation: держать фокус на общей политике и future decision criteria.

- [Риск] Правило максимизации reuse превратится в догму.
  → Mitigation: явно фиксировать условия, при которых `build` остаётся правильным выбором.
