## Техническая проработка

Технические детали реализации ведутся в GitHub issue:
- https://github.com/sobakapav/desengine/issues/10

OpenSpec в этом change фиксирует продуктовые цели, границы и критерии приемки.

## Определения

- **Development Mode**: пользовательский сценарий «работаю над проектом», в отличие от «прохода обучения/уровней».
- **Project Workspace**: контейнер для данных и настроек, которые должны быть изолированы между проектами.

## Минимальная модель данных

Предлагаемая минимальная структура:

- `Project`:
  - `id`
  - `title`
  - `createdAt`
  - `updatedAt`
  - `settings` (минимум: `uiKitId`, `uiMode`)
- `ActiveProjectId`: выбранный проект в UI (в состоянии приложения).
- `ProjectData`: ключ-значение или структурированная область для доменных данных (MVP — достаточно, чтобы начать scoping).

Хранилище:

- на первом шаге допускается локальное (например, localStorage/IndexedDB) при условии чёткого контракта и возможности последующего переноса в серверное хранилище.

## Интеграция в существующие потоки

Сначала интегрируем проектность там, где уже есть явная потребность:

- Sandpack preview (выбор UI kit и режим `html-tags`) — через `project.settings`.
- Экран/контур работы с задачами — должен работать «внутри проекта» (фильтрация/данные/история).

## Миграция и совместимость

Так как ранее проектности не было, нужно предусмотреть:

- «Default project» (автоматически создаваемый/назначаемый), чтобы старые сценарии продолжали работать;
- безопасный перенос части данных в проектный namespace без потери поведения.

## Тестирование и traceability

Минимально:

- Unit: операции с проектами, выбор активного проекта, изоляция project-scoped данных.
- Traceability: соответствие OpenSpec сценариев тестам.
- E2E smoke (желательно): создать проект → сменить активный проект → убедиться, что данные/настройки изолированы.
