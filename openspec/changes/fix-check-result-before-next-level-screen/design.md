## Context

Действующий контракт `task-levels` уже фиксирует, что:

- существует канонический экран результата проверки;
- только после успешной проверки система открывает дальнейший flow следующего уровня или полного завершения задачи.

Значит, дефект находится не в спецификации, а в реализации порядка навигации и/или состояния после `check`.

## Goals

- Восстановить правильный порядок пользовательских экранов после успешной проверки.
- Сделать экран результата проверки обязательной первой точкой после `check`, если результат проверки сформирован.
- Зафиксировать это browser-проверкой, а не только unit-логикой.

## Non-goals

- Не вводить новую модель transition-screen.
- Не менять semantics успешной проверки и завершения уровня.
- Не расширять change на неуспешные проверки, если их порядок экранов не затронут этим же дефектом.

## Decisions

1. Экран результата проверки должен иметь приоритет над переходом к следующему уровню.
   - Если успешный `check` формирует отдельный check-result screen, сначала пользователь должен увидеть именно его.

2. Переход на следующий уровень не должен стартовать раньше завершения check-result phase.
   - Любой auto-navigation, который уводит пользователя на следующий уровень до отображения результата проверки, считается нарушением контракта.

3. Приёмка change должна быть browser-level.
   - Unit-слой может помочь локализовать state machine, но окончательное доказательство должно фиксировать реальный порядок экранов.

## Risks / Trade-offs

- [Риск] В коде могут быть два конкурирующих источника навигации: check-result transition и next-level transition.
  → Mitigation: локализовать явный владелец перехода после успешного `check` и убрать гонку.

- [Риск] Исправление может случайно сломать flow полного завершения задачи на последнем уровне.
  → Mitigation: в change явно проверить различие между `next level` и `done` path.
