## Why

Сейчас пользователь вводит уточняющий промпт обычным текстом, а всё остальное собирает система. Это хороший базовый путь, но части аудитории может понадобиться более «инструментальный» режим: **конструировать промпт** из доступных блоков (навыки, данные, контекст проекта, готовые инструкции, схемы вывода).

Чтобы двигаться в эту сторону, нужен change, который:

- фиксирует цель и минимальный контракт конструктора;
- не ломает текущий UX простого текстового ввода;
- задаёт архитектурные рамки для дальнейшего расширения.

## What Changes

- Вводим альтернативный режим ввода: **Prompt Builder** (конструктор промптов).
- Prompt Builder собирает итоговый промпт (и/или structured prompt) из блоков:
  - `userText` (текущая строка уточнения);
  - `skills` (выбранные навыки/шаблоны);
  - `data` (выбранные данные/артефакты проекта, если есть);
  - `constraints` (формат ответа, стиль, запреты);
  - `tools` (если в системе есть инструментальные подсказки/контекст).
- Вводим контракт:
  - как хранится конфигурация сборки (draft/save);
  - как рендерится финальный промпт (preview);
  - как происходит «прогон» (execute) и логирование результата.
- Сохраняем базовый режим: простой текстовый ввод остаётся дефолтным, а Prompt Builder — опциональным.

## Non-goals

- Полная визуальная IDE для промптов на первом шаге.
- Автоматическое «магическое» построение идеального промпта.
- Командная библиотека блоков (позже, отдельный change).

## Capabilities

### New Capabilities
- `prompt-builder`: сборка промпта из блоков.

### Modified Capabilities
- `task`: запуск LLM-потока получает альтернативный вход (builder-конфиг).
- `experience` (если включён): builder должен логироваться как часть опыта (блоки → итоговый промпт → результат).

## Acceptance Criteria

- Есть минимальный контракт данных Prompt Builder (что такое «блоки», как они сериализуются).
- Можно собрать промпт из нескольких блоков и увидеть preview итогового текста/структуры.
- Можно выполнить запуск тем же пайплайном, что и сейчас, без форка всей логики.
- Есть тестовая стратегия (unit + traceability; опционально e2e smoke) и команды проверки.
