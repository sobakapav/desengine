## Context

Текущий контракт task progression логичен с точки зрения модели обучения: следующая ступень той же задачи открывается сразу. Но пользовательское восприятие может быть другим: после локального успеха человек ожидает вернуться в обзор уровня и выбрать, что делать дальше.

Это конфликт не correctness, а UX-preference против текущего product-flow.

## Goals

- Зафиксировать гипотезу без преждевременной смены контракта.
- Подготовить почву для downstream UX-research или implement change.

## Non-goals

- Не ломать текущий `task-levels` контракт в этом change.
- Не подменять UX-гипотезой уже работающий progression model.

## Decisions

1. Жалоба переводится из списка отказов в `idea`, а не в `fix`.
2. Idea живёт в орбите `dispatcher-ux` через roadmap `ux-quality`.

## Risks

- Возврат к списку задач может замедлить пользователей, которым удобнее сразу двигаться в следующий уровень той же задачи.
- Изменение может конфликтовать с обучающей логикой «держать контекст задачи до конца».

## Open Questions

- Нужен ли единый default flow или настраиваемый post-success route.
- Нужно ли различать прохождение внутри задачи и завершение последнего уровня задачи.
