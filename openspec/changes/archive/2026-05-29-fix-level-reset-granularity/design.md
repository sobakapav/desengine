## Контекст

Модель задач уже знает про уровень, его старт, завершение и переходы. Но reset пока остаётся coarse-grained операцией на всю задачу. Для одноуровневого сценария это терпимо, для многоуровневого — создаёт лишнюю потерю состояния и прямое пользовательское раздражение.

Жалоба здесь не про “хочется новую фичу вообще”, а про то, что текущая операция восстановления слишком грубая относительно уже существующей level-based модели.

## Решение

1. Зафиксировать два разных сценария:
   - reset current level;
   - reset whole task.
2. Для level reset определить, что именно очищается:
   - рабочие файлы текущего уровня;
   - prompt history и check attempts текущего уровня;
   - статус current level.
3. Явно определить, что сохраняется:
   - пройденные предыдущие уровни;
   - их результаты и общий маршрут задачи.
4. Отразить различие в UI и тексте подтверждения, чтобы пользователь не путал scope операции.

## Проверочный слой

- Затронутые capability/scenario:
  - `iteration` / reset и история промптов;
  - `user-progress` / состояние уровней и текущего уровня;
  - `task-levels` / возврат к началу текущего уровня.
- Уровень проверки: `component/browser`.
- Команда: `npm run test:e2e -- test/e2e/level-reset-granularity.spec.ts`

Если реализация начнётся с server-side unit coverage до UI, это допустимо, но итоговый change должен иметь browser proof на пользовательский сценарий reset current level.
