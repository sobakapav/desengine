## Контекст

Система уже знает про текущий уровень, его рабочие файлы, историю уточнений и переходы между уровнями. Полный reset задачи остаётся доступным, но для UX этого недостаточно: пользовательский recovery path должен соответствовать уровневой модели, а не игнорировать её.

Архивный `fix-level-reset-granularity` уже описал нижележащий контракт. Для `dispatcher-ux` важен именно entrypoint и пользовательское понимание действия:

- когда доступен reset текущего уровня;
- чем он отличается от полного reset;
- какое подтверждение видит пользователь;
- как быстро он возвращается к началу уровня без потери пройденных шагов.

## Цели

- Превратить level reset в явный и понятный UX-сценарий.
- Удержать различие между “сбросить уровень” и “сбросить задачу”.
- Доказать через browser path, что действие работает как пользователь ожидает.

## Non-goals

- Не перестраивать всю progression-модель.
- Не добавлять произвольный reset для любых ранее пройденных уровней.

## Направление реализации

1. Восстановить актуальный contract level reset из архивного change и текущего кода.
2. Добавить/вернуть пользовательский entrypoint и понятный confirm path.
3. Проверить browser-сценарий: level-scoped state очищается, а пройденные уровни сохраняются.

## Риски

- Если ограничиться только UI без корректной state boundary, действие будет выглядеть правильно, но ломать прогресс.
- Если ограничиться только серверной операцией без UX-разведения, пользователь останется в путанице между двумя reset-действиями.
