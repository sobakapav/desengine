## Context

В текущем состоянии читаемость кода неоднородна: часть модулей хорошо документирована, часть требует контекстного знания и ручного разбора. Это повышает риск регрессий при правках и увеличивает время на onboarding. Change задает единый контракт практик и способ проверки в рамках существующего тестового слоя без изменения install-critical инфраструктуры.

## Goals / Non-Goals

**Goals:**

- Ввести единый минимальный стандарт читаемости для функций, типов, констант и файлов.
- Сделать стандарт проверяемым, а не только рекомендацией в документации.
- Зафиксировать интеграцию с OpenSpec traceability и общими командами тестирования.
- Обеспечить поэтапное внедрение в legacy-код через прозрачные исключения и сроки закрытия.

**Non-Goals:**

- Полный одномоментный рефакторинг всего репозитория.
- Замена линтера/сборщика/Node.js/Next.js/Turbopack.
- Введение runtime-зависимостей, влияющих на запуск приложения.

## Decisions

1. Capability-first подход:
   - вводим новый capability `code-readability` как источник требований;
   - дополняем `testing-layer`, чтобы читаемость была частью проверяемого контракта.
   - Альтернатива: оставить только markdown-гайд без spec. Отклонена, так как не даёт traceability и контролируемого внедрения.

2. Проверяемый минимум вместо «идеального стиля»:
   - обязательный минимум: комментарии к экспортируемым сущностям, запрет неочевидных сокращений, именованные константы вместо магических литералов, контроль избыточной сложности;
   - дополнительные стилистические рекомендации остаются необязательными.
   - Альтернатива: полный style-guide с десятками правил. Отклонена как дорогая в старте и сложная в принятии.

3. Явные soft-limit по размеру:
   - базовые пороги по умолчанию: до 300 строк на production `*.ts`/`*.tsx` файл и до 60 строк на функцию (без пустых строк и комментариев);
   - для test/storybook допускается мягкий порог до 450 строк на файл с тем же правилом дробления по функциям;
   - превышение возможно только с документированным исключением (причина, владелец, срок закрытия).
   - Альтернатива: оставить «разумный размер» без чисел. Отклонена, так как слишком вариативно трактуется в ревью.

4. Контракты предсказуемости API и потока выполнения:
   - ошибки возвращаются в едином типизированном формате;
   - nullability проверяется на boundary-уровне, а не размазывается по всей цепочке вызовов;
   - boolean-trap параметры запрещены в публичных и доменных функциях;
   - для нетривиальных экспортируемых API обязателен короткий usage-пример.
   - Альтернатива: оставить эти правила на усмотрение автора PR. Отклонена из-за высокой вариативности и повторяющихся дефектов.

5. Изоляция сайд-эффектов и async-безопасность:
   - I/O, env, время, сеть и файловые операции выносятся в адаптеры/инфраструктурные модули;
   - доменная логика остается максимально чистой;
   - floating promises запрещены, асинхронные ошибки обрабатываются явно.
   - Альтернатива: смешивать эффектный и доменный код в одном месте. Отклонена, так как снижает тестируемость и читаемость.

6. Поэтапное внедрение:
   - новые/изменяемые модули должны соответствовать правилам сразу;
   - legacy-часть закрывается по плану через `coverage-plan.json` с причиной и этапом.
   - Альтернатива: одномоментное ужесточение для всего репозитория. Отклонена из-за высокого риска блокировки разработки.

7. Единый слой запуска проверок:
   - проверка читаемости включается в существующий цикл `test:unit` + `test:traceability`;
   - расширенный прогон допускается через `test:full`.
   - Альтернатива: отдельная ручная проверка «по договоренности». Отклонена как непредсказуемая и неаудируемая.

## Risks / Trade-offs

- [Риск] Рост времени ревью из-за новых правил на старте.
  → Mitigation: ограничить обязательный минимум и добавить примеры «до/после».

- [Риск] Ложные срабатывания статических правил.
  → Mitigation: фиксировать исключения явно и ограниченно по времени, с владельцем и этапом закрытия.

- [Риск] Избыточные комментарии «очевидного» кода.
  → Mitigation: в guidance описать критерий полезного комментария: намерение, допущения, побочные эффекты, а не пересказ строки кода.

- [Риск] Конфликт с текущим темпом поставки.
  → Mitigation: rollout по приоритетным зонам, не блокируя весь legacy.

- [Риск] Пороговые значения окажутся слишком строгими или мягкими для отдельных доменов.
  → Mitigation: зафиксировать baseline в config и пересматривать пороги только отдельным change с ретроспективой по фактическим нарушениям.

- [Риск] Новые правила дадут много нарушений в legacy-коде.
  → Mitigation: строгий режим для новых/изменяемых участков и time-boxed исключения для legacy.

## Migration Plan

1. Утвердить требования в OpenSpec (`code-readability` + delta `testing-layer`).
2. Подготовить правила проверки и короткий playbook для команды.
3. Включить обязательность для новых изменений.
4. Поэтапно закрывать legacy-участки по `coverage-plan.json` до полного соответствия.

## Open Questions

- Нужны ли разные уровни строгости для production-кода и тестовых helpers.
- Какая метрика rollout будет основной: доля модулей без исключений или доля PR без readability-замечаний.
- Включать ли browser/component-уровень для демонстрации читаемости UI-модулей или оставить static/unit как обязательный минимум.
