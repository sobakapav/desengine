# Design: fix-release-state

## Контекст

На странице `/system` ресурс `system-release` показывает состояние актуальности кода относительно последнего релиза на `origin`.

Проблема: в успешном сценарии (код соответствует последнему релизу) пользователь мог видеть предупреждение из-за того, что проверка remote-тегов через сеть недоступна (offline) или выполняется из неправильного каталога при запуске через `npm run start` (standalone сборка).

## Решение

1) **Нормализация корня репозитория для git-команд**

Диагностика релиза должна выполнять `git` в корне репозитория, независимо от того, откуда запущен Node-процесс.

Для этого `lib/system/release.ts` ищет репозиторий вверх по дереву от `process.cwd()` по `package.json` с `name=desengine`. Если не найдено — использует fallback от `import.meta.url` (аналогично серверному конфигу).

2) **Offline-режим не создаёт ложную тревогу**

Если список remote-тегов (`origin`) получить невозможно, но `HEAD` находится на **точном релизном теге** (`git describe --exact-match`), то это считается допустимым состоянием `upToDate` и не превращается в warning.

Если точного тега нет, а есть только ближайший тег, состояние считается `development` (как и прежде: нерелизное состояние не блокирует работу).

## Границы

- Change не изменяет обработку случаев, когда код реально отстаёт от релиза (`updateAvailable`).
- Change не добавляет механизмов авто-восстановления или авто-обновления.

## Проверки

- Unit: `npm run test:unit`
- Traceability: `npm run test:traceability`
