## Контекст

Сейчас pipeline iterate оценивает только формальную успешность structured-ответа и записи файлов. Если payload корректен, но весь контент совпадает с уже существующим, система всё равно:
- очищает прошлый check result;
- регистрирует prompt для текущего уровня;
- записывает prompt-history;
- показывает пользователю сообщение об успешном применении.

Такой contract делает невозможным честное различение между:
1. реальным изменением кода;
2. no-op ответом модели;
3. ответом, в котором весь полезный diff был отфильтрован allowlist/cleanup-логикой.

## Решение

1. Ввести отдельный результат iterate для no-op сценария.
2. Явно вычислять причину no-op:
   - модель вернула те же файлы;
   - все изменения ушли в запрещённые файлы;
   - результат был очищен post-write cleanup.
3. Протащить этот результат до UI:
   - не показывать “Уточнение применено”;
   - показывать понятный статус и actionable текст;
   - решить, должен ли такой no-op сжигать prompt limit или нет.
4. Зафиксировать правило в OpenSpec и unit coverage, чтобы интерфейс не называл no-op успешным изменением.

## Проверочный слой

- Затронутые capability/scenario:
  - `iteration` / пользователь запускает уточняющий промпт;
  - `user-progress` / расходование promptsUsed;
  - `task` / feedback рабочего экрана.
- Уровень проверки: `unit`.
- Команда: `npm run test:unit -- test/unit/task-iterate-noop-feedback.test.ts`

Если продуктово будет решено сохранять no-op как потраченную попытку, это всё равно должно быть явно и честно отражено в UI и в contract-тестах.
