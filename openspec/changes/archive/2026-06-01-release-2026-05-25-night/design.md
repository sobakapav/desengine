## Контекст

`release-2026-05-25-night` не меняет код и не вводит новый продуктовый контракт. Его задача уже описана в `proposal.md`: выступать релизной меткой для ночной волны улучшения `test:integration`, чтобы delivery был виден как единый срез, а не как набор разрозненных implement changes.

Проблема текущего состояния в том, что change оформлен неполно для схемы `spec-driven`: отсутствуют `design.md`, `tasks.md` и delta specs. Из-за этого release нельзя штатно архивировать, хотя по смыслу он уже выполняет функцию релизной группировки.

## Решение

Нужно оформить release как документирующий change без расширения поведенческой области:

1. Явно зафиксировать, что release не становится `parent_change` для downstream implement changes и не подменяет `dispatcher-test-system`.
2. Закрепить состав integration-wave как набор changes, объединённых через `release_ref`.
3. Добавить delta spec на уровне `admin-tools`, которая использует уже существующий контракт release/`release_ref` как частный пример этого релиза.
4. Описать тестовый след как static/contract-проверку оформления и ссылочной целостности.

## Границы

В этот change входит:

- описание состава integration-wave;
- фиксация роли `release_ref` для релизного среза от 25 мая;
- тестовая трассировка на уровне OpenSpec/admin-tools.

В этот change не входит:

- изменение кода продукта;
- изменение стратегической иерархии downstream implement changes;
- введение новых CLI-команд, новых ролей change или новых metadata-полей.

## Риски и их контроль

- Риск: release будет выглядеть как новый продуктовый контракт.
  Контроль: delta spec опирается на уже существующее требование про release и `release_ref`, а не добавляет новый механизм.
- Риск: release начнут воспринимать как замену dispatcher-контексту.
  Контроль: в design и spec явно указано, что downstream changes сохраняют `parent_change`, а release служит только релизной меткой.

## Проверка

- Уровень: static/contract.
- Команда для внешней проверки: `npm run test:traceability`.
- Что должно подтвердиться: release change оформлен полностью, а downstream integration changes сохраняют корректную ссылку на релиз через `release_ref`.
