# Инструкция по миграции onboarding-задачи в режим `проект -> workflow -> проверка/чеклист -> результат`

## Для кого этот документ

Документ нужен контент-менеджеру, который переводит существующие onboarding-задачи со старой
level-центричной схемы на новый пользовательский путь:

`проект -> workflow -> проверка/чеклист -> результат`

Здесь не описывается переписывание runtime или UI-кода. Цель документа: дать понятную схему, как
переупаковать содержимое одной onboarding-задачи и её metadata так, чтобы downstream UI-волны могли
показать новый режим без повторного исследования структуры контента.

## Что есть сейчас

Текущая onboarding-схема в репозитории устроена так:

- каждая задача живёт в `onboarding/tasks/<taskId>/`;
- в `config.json` задачи сейчас хранится только минимум:
  - `images.*`
  - `maxLevel`
- основная didactic-структура задачи разложена по `levels`:
  - task-specific подсказки: `onboarding/tasks/<taskId>/levels/level-*/tip.md`
  - глобальные описания уровней: `onboarding/levels/level-*/config.json`, `overview.md`
  - скрытые prompts: `onboarding/prompts/levels/level-*/start.njk`, `iterate.njk`, `check.njk`
- runtime и типы задачи тоже завязаны на уровне:
  - `TaskProgress.currentLevel`
  - `TaskLabContext.levelId`, `levelNumber`
  - `TaskCheckResult.levelId`, `levelNumber`, `levelTitle`
  - `TaskConfig.maxLevel`

Итог: сейчас пользовательский путь всё ещё читается как прохождение уровней, даже если внутренняя
workflow-проекция уже умеет мапить level progress на workflow points.

## Что должно получиться

После миграции контент onboarding-задачи должен описывать не лестницу уровней, а рабочую цепочку:

1. `Проект`
   Точка входа, где задаются контекст проекта и базовые настройки.
2. `Workflow`
   Набор шагов работы над задачей, понятный пользователю как последовательность практических этапов.
3. `Проверка/чеклист`
   Критерии, по которым пользователь понимает, что шаг готов к проверке и что именно будет считаться
   успешным результатом.
4. `Результат`
   Что считается достигнутым выходом по шагу и по задаче в целом.

Важно: на текущем этапе legacy runtime ещё может пользоваться level-данными как внутренним мостом.
Но контент и metadata надо готовить так, будто главным пользовательским языком уже являются проект,
workflow, проверка и результат.

## Что считать старой схемой

Ниже поля и сущности, которые нельзя оставлять главным пользовательским источником смысла:

| Старая сущность | Где живёт сейчас | Почему этого недостаточно |
| --- | --- | --- |
| `maxLevel` | `onboarding/tasks/<taskId>/config.json` | Пользователю ничего не говорит о реальном ходе работы |
| `level-*` как шаги задачи | `onboarding/tasks/*/levels/*`, `onboarding/levels/*` | Описывает механику прохождения, а не рабочий смысл |
| `start/iterate/check` prompts уровня | `onboarding/prompts/levels/*` | Привязаны к level-номеру, а не к workflow-этапу |
| `tip.md` уровня | `onboarding/tasks/*/levels/level-*/tip.md` | Подсказка есть, но не ясно, к какому результату шага она ведёт |
| `TaskCheckResult.level*` | runtime result | Результат описан как исход уровня, а не как итог шага работы |

Это не значит, что level-данные надо немедленно удалить. Значит, что они больше не должны быть
основой контентной модели.

## Mapping старой структуры на новую

| Что было | Что становится | Где хранить как источник смысла | Для чего нужно UI |
| --- | --- | --- | --- |
| `taskId` | workflow template или типовая задача | task/workflow-слой | Чтобы стартовать типовую работу без поиска “свободного task slot” |
| `images.base`, `images.variants` | референсы проекта и компонента | project context | Чтобы проект и шаги работы знали, с какими материалами работает пользователь |
| `maxLevel` | число workflow-шагов или bridge-ограничение runtime | workflow description | Чтобы UI показывал прогресс по шагам, а не “уровень N из M” |
| `level-*/tip.md` | описание шага workflow | workflow step | Чтобы экран работы объяснял текущий этап человеческим языком |
| `onboarding/levels/*/config.json` | техданные шага и bridge на legacy runtime | workflow step + runtime bridge | Чтобы сохранить совместимость, но не тащить level в пользовательский язык |
| `start.njk` уровня | стартовый prompt шага | workflow step | Чтобы генерация стартовала из смысла текущего шага |
| `iterate.njk` уровня | prompt доработки шага | workflow step | Чтобы повторная работа была привязана к этапу, а не к номеру уровня |
| `check.njk` уровня | prompt проверки шага | check/result block | Чтобы проверка была описана как проверка готовности шага |
| `TaskCheckResult` по уровню | результат шага | result block | Чтобы UI показывал “что готово / что не готово”, а не только исход level check |
| prompt history | история работы по шагам | workflow/result layer | Чтобы можно было объяснить последнюю активность и контекст повторной работы |

## Куда раскладывать metadata

### 1. Project context

Сюда относится то, что описывает входной контекст задачи, а не конкретный шаг:

- `project.id`
- `project.title`
- `project.settings.uiKitId`
- исходные референсы:
  - `images.base`
  - `images.variants`
- если нужно, project-level пояснение, какой компонент или экран собирается

Project context отвечает на вопрос: “В каком проекте и с какими исходными вводными пользователь
вообще выполняет эту задачу?”

### 2. Workflow description

Сюда относится то, что описывает саму работу по шагам:

- `workflow.id`
- `workflow.title`
- список `workflow.steps`
- для каждого шага:
  - `id`
  - `title`
  - `goal`
  - `prompt`-смысл старта и доработки
  - связанные `fileIds`
  - bridge на legacy level, если он пока нужен

Workflow description отвечает на вопрос: “Из каких этапов состоит задача и что пользователь делает
на каждом этапе?”

### 3. Проверка и результат

Сюда относится всё, что нужно для проверки готовности и показа исхода:

- `checklist` шага
- критерии проверки
- prompt проверки
- пользовательские статусы результата:
  - готово к проверке
  - проверка пройдена
  - нужна доработка
  - повторить проверку
- итоговый результат шага
- итоговый результат задачи

Этот слой отвечает на вопрос: “Как понять, что шаг завершён, и что показать пользователю после
проверки?”

## Минимальная целевая схема metadata

Ниже не runtime-контракт и не обязательный JSON-формат хранилища. Это каноническая схема, по которой
контент-менеджеру нужно собирать содержание задачи.

```json
{
  "project": {
    "id": "project-alpha",
    "title": "Alpha",
    "uiKitId": "ant",
    "references": {
      "baseImage": "base",
      "variantImage": "variants"
    }
  },
  "workflow": {
    "id": "image-to-component-workflow",
    "title": "Собрать компонент по референсу",
    "steps": [
      {
        "id": "ui-kit-component",
        "title": "Собрать базовый компонент",
        "goal": "Пользователь получает рабочий каркас компонента в выбранном UI kit.",
        "fileIds": ["markup", "component"],
        "legacyLevelHint": 1,
        "prompts": {
          "start": "Собери базовый компонент по референсу.",
          "iterate": "Доработай каркас компонента без отхода от референса."
        }
      },
      {
        "id": "styles",
        "title": "Довести стилизацию",
        "goal": "Компонент визуально совпадает с референсом по ключевым признакам.",
        "fileIds": ["styles"],
        "legacyLevelHint": 2,
        "prompts": {
          "start": "Добавь стилизацию.",
          "iterate": "Исправь расхождения по визуалу."
        }
      }
    ]
  },
  "check": {
    "steps": [
      {
        "stepId": "ui-kit-component",
        "checklist": [
          "Есть базовая структура компонента.",
          "Компонент использует выбранный UI kit.",
          "Основной файл готов к дальнейшей стилизации."
        ],
        "checkPrompt": "Проверь, что базовый компонент собран и пригоден для следующего шага."
      }
    ]
  },
  "result": {
    "stepStatuses": ["not_started", "in_progress", "ready_for_check", "passed", "needs_rework"],
    "taskOutcome": "Пользователь получает компонент, который можно открыть как результат workflow."
  }
}
```

## Как переработать одну существующую onboarding-задачу

### Шаг 1. Выписать текущие исходники задачи

Для выбранной задачи соберите:

- `onboarding/tasks/<taskId>/config.json`
- `onboarding/tasks/<taskId>/levels/**/tip.md`
- связанные `onboarding/levels/level-*/config.json`
- связанные `onboarding/prompts/levels/level-*/start.njk`, `iterate.njk`, `check.njk`

На этом шаге не нужно ничего переписывать. Нужно просто зафиксировать, какие level-данные реально
используются у этой задачи.

### Шаг 2. Сформулировать проектный вход

Для этой задачи явно ответьте:

- в каком проектном контексте пользователь должен её проходить;
- какой `uiKitId` считается основным;
- какие референсы нужны на входе;
- что за компонент или экран пользователь в итоге собирает.

Если на этом шаге приходится говорить “пользователь просто проходит уровень”, значит проектный вход
ещё не сформулирован.

### Шаг 3. Разложить старые уровни на workflow-шаги

Для каждого используемого уровня определите:

- какой у него реальный смысл;
- какой артефакт или промежуточный результат он должен дать;
- какие файлы он затрагивает;
- нужен ли он как отдельный пользовательский шаг или это только legacy bridge.

Практическое правило:

- если несколько уровней ведут к одному и тому же пользовательскому результату, объединяйте их в
  один workflow-шаг;
- если один уровень покрывает разные смысловые работы, разбивайте его на несколько шагов в
  workflow-описании, даже если runtime пока продолжает использовать один bridge-level.

### Шаг 4. Переписать подсказки в язык шага, а не уровня

Старый вопрос:

- “Что нужно сделать на уровне 2?”

Новый вопрос:

- “Какой результат должен дать шаг `styles` и что именно надо исправить, если он не готов?”

Для каждого шага подготовьте:

- короткую цель;
- стартовую инструкцию;
- инструкцию на доработку;
- список затрагиваемых файлов;
- ожидаемый результат шага.

### Шаг 5. Вынести проверку в отдельный check/result слой

Для каждого шага нужно отдельно сформулировать:

- чеклист готовности к проверке;
- что проверка считает успешным исходом;
- какие типовые причины должны вести к доработке;
- как выглядит результат шага в UI.

Плохой вариант:

- “Проверка уровня не пройдена”.

Нормальный вариант:

- “Базовый компонент собран, но не использует выбранный UI kit”.

### Шаг 6. Оставить legacy level только как bridge

Если runtime пока ещё требует:

- `maxLevel`
- `levelId`
- `levelNumber`
- level-specific prompts

их можно сохранять, но только как технический мост. В пользовательском описании задачи нельзя
делать их основной моделью.

## Минимальные примеры переноса данных

### Пример 1. Что делать с `config.json` задачи

Было:

```json
{
  "images": {
    "base": { "width": 151, "height": 32 },
    "variants": { "width": 430, "height": 1041 }
  },
  "maxLevel": 5
}
```

Как мыслить после миграции:

- `images.*` становятся частью project context и входных референсов;
- `maxLevel` перестаёт быть главным пользовательским описанием прогресса;
- если runtime пока требует `maxLevel`, его можно сохранить как bridge, но рядом должна появиться
  workflow-структура шагов.

### Пример 2. Что делать с `tip.md` уровня

Было:

- `onboarding/tasks/<taskId>/levels/level-2/tip.md`

Становится:

- описание workflow-шага `styles`
- цель шага
- что пользователь должен поправить
- какие файлы относятся к этой работе

### Пример 3. Что делать с hidden check prompt

Было:

- `onboarding/prompts/levels/level-2/check.njk`

Становится:

- prompt проверки шага `styles`
- плюс явный checklist, который можно показать человеку

## Checklist готовности миграции

Onboarding-задача считается готовой к новому режиму, если на неё можно ответить “да” по всем пунктам:

- у задачи есть явный проектный вход, а не только `taskId` и `maxLevel`;
- понятно, какой проект, какой `uiKitId` и какие референсы нужны на старте;
- шаги работы описаны как workflow-этапы с целью и результатом;
- для каждого workflow-шага понятны связанные файлы;
- старые `level-*` сопоставлены с workflow-шагами;
- есть явное разделение на `project`, `workflow`, `check`, `result`;
- есть checklist готовности к проверке хотя бы для каждого основного шага;
- hidden prompts можно прочитать как prompts шага, а не как безымянные prompts уровня;
- результат проверки можно показать пользователю как исход шага работы;
- legacy level-данные, если они ещё нужны, обозначены как bridge, а не как главный язык задачи.

## Что передавать downstream UI-волнам

После переработки одной onboarding-задачи контент-менеджер должен передать дальше не “набор
уровней”, а такой комплект:

- project context задачи;
- список workflow-шагов с целями и файлами;
- check/result блок по каждому шагу;
- mapping старых levels на новые шаги;
- пометку, какие legacy level-поля пока сохраняются только ради совместимости runtime.

Именно этот набор позволяет UI-волнам переводить интерфейс onboarding на новый пользовательский путь
без очередного ручного исследования исходной задачи.

## Связь с capability и проверкой

Затронутые capability/scenarios на planning-уровне:

- `task`: onboarding-задача перестаёт описываться только через level progress и готовится к новому
  task surface.
- `workflow`: onboarding-задача получает явное разложение на workflow-шаги.
- `projects`: onboarding-задача получает project-aware точку входа.

Проверка этого change:

- уровень: `static/contract`
- команда: `npm run test:traceability`

Mock/fixture-данные и live credentials не требуются, потому что change поставляет content-migration
guide, а не меняет runtime напрямую.
