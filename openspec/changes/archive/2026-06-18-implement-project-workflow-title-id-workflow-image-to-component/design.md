## Контекст

- Project boundary уже существует как отдельный пользовательский раздел.
- Компоненты проекта уже умеют храниться отдельно от задач и могут получить `backing task`.
- Workflow уже запускается через существующий lab runtime, но пользовательский путь пока собран из разрозненных кусков и слишком слабо подсказывает следующий шаг.

## Решение

1. Не вводить новый runtime-маршрутизатор и не пересобирать storage-модель.
   Этот change использует уже существующие project registry, component registry и workflow entrypoint.

2. Сделать создание проекта явной первой ступенью пользовательского пути.
   После создания проекта пользователь должен сразу видеть, что делать дальше: открыть проект и перейти к компонентам.

3. На странице проекта сделать маршрут по компонентам более операционным.
   Пользователь должен видеть, что:
   - в проекте можно держать несколько компонентов;
   - каждый компонент является отдельной точкой входа в workflow;
   - запуск и продолжение workflow происходят из карточки компонента;
   - после запуска у компонента появляется повторно используемая workflow-сессия.

4. Усилить project-facing surface, а не расширять внутреннюю модель исполнения.
   Мы добавляем понятные CTA, короткие пользовательские пояснения и surface-индикаторы по компонентам, но не меняем underlying task/workbench engine.

5. Зафиксировать это как testable contract.
   Unit-контракты должны явно проверять:
   - пользовательский путь из project registry к project page;
   - наличие практичных CTA для перехода в проект и workflow;
   - модель работы с несколькими компонентами одного проекта.
