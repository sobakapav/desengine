## Context

Сейчас bounded timeout существует только для скрытого initiator-запуска. Для обычных пользовательских действий `iterate` и `check` система полагается на внешнее поведение сети и провайдера.

Это делает именно пользовательский интерактивный цикл менее устойчивым, чем фоновый init-flow.

## Goals

- Ограничить время ожидания для интерактивных LLM-действий.
- Сохранить текущее состояние задачи при timeout.
- Сделать timeout повторяемой и понятной ошибкой.

## Non-goals

- Не менять provider transport layer сверх необходимого для timeout propagation.
- Не добавлять сложный retry-orchestration.

## Decisions

1. `iterate` и `check` получают собственный bounded timeout.
   - Время ожидания должно быть управляемо конфигом и не зависеть от поведения браузера по умолчанию.

2. Timeout обрабатывается как retriable runtime failure.
   - Состояние файлов и прогресса не теряется.
   - UI снимает pending и показывает короткое объяснение.

3. Проверка должна охватывать и runtime, и пользовательский flow.
   - Одного unit-слоя недостаточно; нужен хотя бы один browser/e2e сценарий.

## Risks / Trade-offs

- [Риск] Слишком короткий timeout будет резать легитимно долгие provider ответы.
  → Mitigation: задавать conservative default и оставить возможность конфигурирования.

- [Риск] Timeout добавят только в runtime, но UI останется в неопределённом состоянии на других ошибках.
  → Mitigation: явно проверить снятие pending и текст ошибки в интерактивном сценарии.
