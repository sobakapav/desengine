## Контекст

В проекте уже есть release changes с собственным `release-notes.md`, но этот файл не участвует в обычном жизненном цикле implement/fix change. В результате release notes отстают от фактического delivery-состава и легко превращаются в историческую заметку вместо рабочего пользовательского журнала изменений.

## Решение

1. Зафиксировать в `admin-tools`, что release-linked implement/fix change перед закрытием обязан иметь свой `artifacts/release-note.md`.
2. Сделать этот артефакт user-facing по формату:
   - что меняется для пользователя;
   - как это влияет на пользователя;
   - как вручную проверить, что change реально доехал.
3. Научить `os:close` переносить этот артефакт в `release-notes.md` релиза до архивирования change.
4. Добавить idempotent guard: повторный close-path или заранее внесённая запись не должны плодить дубликаты.

## Риски и ограничения

- Автоматизация не умеет сама превращать технический proposal в хороший пользовательский текст, поэтому качество записи остаётся обязанностью исполнителя change.
- Правка не закрывает ретроспективно все старые changes: она задаёт новый процесс и даёт старт актуальному релизу.
- `os:close` остаётся инструментом только для implement/fix и не превращается в отдельный release-publisher.
