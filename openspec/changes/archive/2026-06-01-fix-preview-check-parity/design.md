## Контекст

Симптом выглядит как расхождение двух product-контуров:

- preview runtime пытается отрисовать пользовательский результат и падает на component/runtime path;
- check pipeline принимает задачу по собственным критериям и не считает preview failure блокирующим.

Это не обязательно означает, что один из контуров “сломался вообще”. Возможно, они проверяют разные инварианты. Но пользовательский продуктовый контракт от этого не становится лучше: если preview для учебной задачи не даёт увидеть результат, успех проверки без объяснения выглядит ошибкой системы.

## Цели

- Понять, какой именно drift существует между preview и check.
- Исправить product contract так, чтобы broken preview и successful check не сочетались молча.
- Зафиксировать guard на этот сценарий в browser-level проверке.

## Non-goals

- Не превращать любую preview-ошибку в автоматический полный запрет check без анализа дидактического контракта.
- Не переписывать весь Sandpack/runtime/check flow в одном change.

## Направление реализации

1. Собрать repro с конкретным кодом или task state, где preview падает на `Element type is invalid`.
2. Проверить, что именно получает check и почему он считает решение успешным.
3. Либо исправить preview path, либо ужесточить/уточнить check contract, либо добавить честную user-facing диагностику о различии контуров.

## Риски

- Если просто сделать check строже без локализации причины, можно повысить число ложных отказов.
- Если ограничиться починкой preview без верификации check path, drift может остаться скрытым.
