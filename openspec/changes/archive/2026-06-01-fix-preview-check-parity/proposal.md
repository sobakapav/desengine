## Why

Пользователь сообщает о повторяющемся дефекте: во время решения задачи preview не показывает результат и вместо него выводит runtime-ошибку вида `Element type is invalid ... got: undefined`, но при этом сама проверка может одобрить задачу.

Такое расхождение ломает доверие к системе:

- пользователь не понимает, видит ли он реальный результат своей правки;
- broken preview выглядит как явный продуктовый дефект;
- успешный check на фоне сломанного preview делает систему непредсказуемой и затрудняет обучение.

## What Changes

- Воспроизвести сценарий, в котором preview ломается, а check остаётся успешным.
- Локализовать источник drift: preview слишком строгий, check слишком слабый или оба контура смотрят на разные артефакты.
- Выровнять preview/check contract так, чтобы пользователь не получал одновременно broken preview и безусловный успешный verdict без объяснимой причины.

## Non-goals

- Не делать preview единственным критерием успеха без анализа check-контракта.
- Не смешивать этот fix с unrelated layout/performance проблемами.
- Не ослаблять проверку задачи только для того, чтобы визуально убрать противоречие.

## Impact

- Пользователь будет понимать, чему доверять: preview и check перестанут противоречить друг другу на одном и том же решении.
- Команда получит локализованный contract drift вместо размытой жалобы “превью сломано, но задача принимается”.
