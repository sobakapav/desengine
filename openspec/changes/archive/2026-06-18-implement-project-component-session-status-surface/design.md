## Контекст

- Родительский `dispatcher-project` уже закрепил project page как canonical user entrypoint для project-facing surfaces.
- Предыдущие implement-change уже сделали две вещи:
  - `ProjectComponent` стал project-scoped сущностью;
  - из карточки компонента можно запустить или переиспользовать backing task для `image-to-component` workflow.

Пробел остаётся в пользовательском чтении состояния. Workflow-readout уже существует на странице проекта отдельным блоком, но сам список компонентов пока не использует этот слой для действий и краткой диагностики.

## Решение

1. Связать карточку `ProjectComponent` с уже загруженным `ProjectWorkflowReadoutSnapshot` по `taskId`.
2. Собрать для карточки компактную session-модель:
   - статус workflow-run;
   - последняя активность;
   - краткий прогресс по пунктам workflow;
   - человекочитаемый task label;
   - текст главного действия (`Работать над компонентом` или `Продолжить работу`).
3. Показать этот session-readout прямо в `ProjectComponentsPanel`, не заставляя пользователя читать отдельный workflow-readout блок ради базовой навигации.

## Границы

- Входит:
  - project-facing readout состояния component workflow-сессии;
  - action label для повторного входа;
  - использование уже доступного `workflowReadout` без нового storage.
- Не входит:
  - новый серверный источник данных по компонентам;
  - изменение orchestration-модели workflow;
  - скрытие backing task из системы полностью;
  - отдельное управление историей итераций.

## Проверяемые последствия

- Если у компонента workflow ещё не запускался, карточка остаётся честной и предлагает старт.
- Если у компонента уже есть связанный task и readout runtime, карточка показывает понятный статус и позволяет продолжить работу из того же места.
- Если task уже назначен, но runtime-readout ещё не проявлен, карточка деградирует безопасно и не ломает вход в workflow.
