## Why

После reset задача и текущий уровень не должны поднимать старую историю уточнений или старый результат проверки из предыдущего состояния. Если после сброса пользователь всё ещё видит устаревшие данные, система нарушает уже зафиксированный reset-контракт и делает повторную попытку прохождения недостоверной.

Проблема относится к bugfix-линии, а не к idea-слою:
- требуемое поведение уже зафиксировано в действующих спеках reset;
- пользователю не нужна новая возможность, нужно восстановление ожидаемого поведения.

## What Changes

- Зафиксировать `fix-check-reset-history-regression` как downstream `fix` change линии `dispatcher-bugfix`.
- Вернуть после reset корректную очистку истории уточнений и результата проверки в пределах того scope, который сбрасывает пользователь.
- Синхронизировать verification change с существующим browser-сценарием reset.

## Non-goals

- Не пересматривать всю progression-модель задачи.
- Не менять UX reset beyond already approved flows.
- Не вводить новый тип reset поверх уже существующих `reset task` и `reset current level`.

## Impact

- После reset пользователь видит действительно чистое состояние для повторной попытки.
- История уточнений и результат проверки больше не расходятся с фактическим состоянием уровня.
- Change получает корректный lineage внутри active bugfix-линии и ближайшего релиза.
