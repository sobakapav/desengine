## Context

В текущей архитектуре Sandpack preview формирует виртуальный проект (файлы, зависимости, entrypoints) и запускает его через `@codesandbox/sandpack-react`. По мере роста требований появляется потребность подключать разные UI kit'ы, но без размазывания конфигурации и списков зависимостей по runtime-коду.

Ключевое требование change: **конфигурация UI kit'ов должна быть вынесена во внешний файл**.

## Goals / Non-Goals

**Goals:**
- Ввести единый интерфейс адаптера UI kit'а к Sandpack payload.
- Вынести все kit-specific данные (npm-пакеты, версии, доп. файлы, bootstrap-обвязка) во внешний конфиг.
- Сделать добавление нового UI kit'а максимально локальным: правка конфига + (при необходимости) небольшой adapter-хелпер без каскадных изменений.
- Зафиксировать безопасный fallback: отсутствие/неизвестность `uiKitId` не ломает preview.

**Non-Goals:**
- Полная реализация и поддержка всех UI kit'ов мира (нужно начать с минимального набора и расширять по мере надобности).
- Переписывание Sandpack preview pipeline целиком.
- Автоматическая установка npm-зависимостей на лету в рантайме (предполагаем, что зависимости должны быть известны и контролируемы).

## Proposed Design

### 1) Внешняя конфигурация UI kit'ов

Добавить внешний файл конфигурации (предварительно: `lib/lab/sandpack-ui-kits.config.ts` или аналогичный путь), который экспортирует набор kit'ов:

- `id`: стабильный идентификатор (например `shadcn`, `mantine`, `mui`).
- `title`: человекочитаемое имя.
- `dependencies`: набор npm-зависимостей, которые должны попасть в Sandpack `package.json` (включая peer зависимости, если нужно).
- `files`: дополнительные/заменяемые файлы виртуального проекта (например `styles.css`, `main.tsx`, provider wrapper, theme setup).
- `sandpack`: опциональные настройки Sandpack (environment/entry, если нужно).

Важное правило: runtime-код не хранит kit-specific списки зависимостей и файлов — он читает их из внешнего конфига.

### 2) Интерфейс адаптера

Ввести минимальный интерфейс, который приводит конфиг к «операциям над payload»:

- `resolveSandpackUiKit(uiKitId) -> adapter | null`
- `applySandpackUiKitAdapter(payload, adapter) -> payload`

Где adapter применяет:
- merge зависимостей в `package.json`;
- добавление/замену файлов;
- (опционально) добавление импорта глобальных стилей/провайдеров в entrypoint.

### 3) Источник выбора `uiKitId`

Зафиксировать одну стратегию (с явным fallback), например:

- `uiKitId` приходит из level/task контракта (предпочтительно, как часть `level-config` или task-specific настроек preview).
- Если `uiKitId` не задан или неизвестен, используется `default` adapter (или отсутствие adapter'а).

Это решение должно быть отражено в OpenSpec (`task` и/или `level-labs`), чтобы поведение было контрактно определено.

## Risks / Trade-offs

- [Supply chain] Внешние npm-пакеты увеличивают риск несовместимостей и размер preview — нужно ограничивать список kit'ов и фиксировать версии.
- [Совместимость] Разные UI kit'ы могут требовать специфических настройкок (CSS reset, providers, peer deps) → интерфейс adapter'а должен позволять расширение, но без превращения в «всё обо всём».
- [Трассируемость] При добавлении новых kit'ов важно не забывать обновлять OpenSpec scenarios и тесты.
