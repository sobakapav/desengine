## Контекст

- Родительский change управляет приоритетом и порядком реализации.
- В проектной линии уже есть user-facing registry проектов и сущность `ProjectComponent`.
- В workflow-линии уже есть `image-to-component-workflow`, coordinator step `Работаем над workflow` и point-driven generation control.
- Но между ними пока нет production bridge: пользователь видит компонент проекта, но не может запустить по нему реальную проектную работу прямо из project surface.

## Решение

1. Сделать `ProjectComponent` рабочей точкой входа в существующий project-owned workflow runtime.
   Для текущей волны компонент не получает отдельную пользовательскую сущность-посредник. Достаточно запустить компонентную линию работы внутри уже существующего проектного контура.

2. Не хранить отдельный legacy runtime id внутри `ProjectComponent`.
   Тогда сущность компонента остаётся простой:
   - один раз создать компонент;
   - запускать и возобновлять по нему работу как часть project session;
   - не тянуть в модель legacy runtime bridges.

3. Добавить project-facing действие `Взять в работу`.
   Действие:
   - фиксирует active project;
   - переводит компонент в `in_progress` внутри project context;
   - отражает запуск линии в project history и workflow readout;
   - оставляет пользователя на странице проекта.

4. Не вводить пока отдельный `component-scoped workflow engine` и не открывать полноценный workbench.
   Этот change закрывает реальную пользовательскую точку входа. Более глубокая execution-модель и unlocked workbench могут появиться позже отдельной волной.

## Компромиссы

- `ProjectComponent` пока не открывает собственную workflow-сессию и не получает отдельный инструментальный экран.
  Это сознательное упрощение текущей волны: пользователь уже может создавать компоненты и запускать по ним линии работы, а система не зависает на полном перепроектировании execution layer.
- Locked workbench shell и более глубокие workflow actions остаются следующей волной.
