## Контекст

Соседний `idea-figma-project-import-adapter` уже удерживает линию импорта внешнего Figma-материала в проект desengine. Но user intent из этой новой ветки другой: не «забрать проект целиком», а «взять конкретный компонент и получить кодовую заготовку».

Это требует отдельного producer-контура, потому что здесь меняются:

- гранулярность входа;
- ожидания от результата;
- ритм повторения workflow;
- downstream ownership для `workbench`, `workflow` и компонентного слоя.

## Goals

- Зафиксировать component-level Figma-to-React как отдельный workflow под `focus-domain`.
- Описать минимальный контракт результата: базовый React-компонент как scaffold, а не визуально точный экспорт.
- Развести эту линию с общим import adapter.
- Подготовить downstream карту producer/dispatcher/implement работ.

## Non-goals

- Не создавать сейчас Figma API contract целиком.
- Не проектировать общий импорт страниц, экранов, токенов и ассетов.
- Не обещать автоматическую раскладку целой иерархии приложения.

## Решение

### 1. Workflow считается повторяемым component-level процессом

Producer фиксирует, что единицей работы является отдельный компонент или variant-group, а не весь проект. Этот workflow должен повторяться многократно и не зависеть от того, импортируется ли параллельно весь Figma-файл.

### 2. Результат считается кодовой заготовкой

Выходной артефакт — базовый React-компонент, пригодный для последующей доработки:

- структура JSX;
- выделенные props и variants, если они читаются из источника;
- базовые placeholders для styling и slots;
- границы того, что осталось ручной работой.

### 3. Линия должна быть отделена от import adapter

Если оставить эту работу внутри import adapter, downstream изменения начнут конфликтовать:

- один поток будет мыслить страницами и файлами;
- другой — компонентами и React-контрактом;
- критерии готовности и тестирования будут разными.

Поэтому producer заранее фиксирует отдельный ownership.

### 4. Downstream changes должны быть узкими

Следующие behavior-change ветки лучше разделять минимум на такие вопросы:

1. выбор и нормализация Figma-компонента как входа;
2. контракт базового React-результата;
3. связка с `workbench` и preview;
4. интеграция с проектным `UI kit`, если она становится обязательной;
5. проверка и traceability для типовых component-shapes.

## Риски и компромиссы

- Если producer оставить слишком общим, его снова начнут трактовать как подпункт import adapter.
- Если обещать визуально точную генерацию, downstream линия станет нереалистичной и потеряет проверяемость.
- Если не зафиксировать scaffold-характер результата, команда будет спорить о критериях «готового компонента».

## Открытые вопросы

- Какой минимальный shape React-компонента должен считаться приемлемым базовым результатом.
- В какой момент variants и props становятся обязательной частью workflow, а не nice-to-have.
- Нужна ли отдельная producer/dispatcher-линия для component hierarchy после появления этого workflow.
