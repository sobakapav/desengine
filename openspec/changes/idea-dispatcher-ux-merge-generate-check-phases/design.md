## Роль idea

- `change_kind=idea`
- `execution_mode=no-code`
- задаёт UX-рамку для дочерних `producer`/`implement`/`fix` changes внутри `dispatcher-ux`

## Контекст

Текущий контракт уже требует отдельной успешной проверки уровня, и это правильно с точки зрения качества результата. Проблема не в самом факте проверки, а в том, как она воспринимается пользователем: интерфейс и последовательность экранов могут внушать, что после «сделать код» начинается ещё одна большая самостоятельная фаза.

Для UX это избыточное когнитивное разделение. Пользователь мыслит не терминами внутренних фаз runtime, а вопросом: «я уже довёл решение до состояния, которое система приняла?».

## Принцип целевого UX

Будущая реализация должна исходить из следующего принципа:

- у пользовательского сценария есть один главный outcome: `Проверка пройдена`;
- генерация, доработка и запуск проверки составляют один контур доведения результата;
- промежуточные статусы допустимы, если они помогают ориентироваться, но они не должны выглядеть как отдельные несвязанные проекты;
- интерфейс в каждый момент должен отвечать на один вопрос: «сколько осталось до принятого системой результата».

## Граница ответственности

Этот idea-change:

- фиксирует продуктовый смысл объединения фаз;
- определяет затронутые UX-области;
- задаёт требования к downstream тестовой формализации.

Этот idea-change не:

- выбирает окончательный UI-паттерн;
- не меняет runtime и не правит copy напрямую;
- не переписывает существующие OpenSpec specs в одиночку без следующего behavior-change.

## Направления downstream-проработки

Ниже то, что должен уточнить следующий change реализации:

- какое основное действие ведёт пользователя к состоянию `Проверка пройдена`;
- где проходит граница между «черновой результат готов» и «можно/нужно запускать проверку»;
- нужно ли автоматически сцеплять окончание генерации с переходом к проверке;
- какие пользовательские статусы оставить видимыми, а какие спрятать как технические;
- как показывать неуспешную проверку так, чтобы это выглядело как продолжение одного цикла улучшения, а не как вход в отдельный второй этап.

## Ожидаемые затронутые контракты

На уровне будущего behavior-change, вероятнее всего, потребуется обновить сценарии в:

- `openspec/specs/task-levels/spec.md`
- `openspec/specs/user-progress/spec.md`
- при необходимости `openspec/specs/task/spec.md` или связанный task-level UX capability, если там фиксируются route/экраны/действия

## Тестовая стратегия для downstream change

Будущий implementation-change должен проверить не только техническую корректность, но и новый UX-контракт:

- static/contract: обновлённые OpenSpec scenarios для `task-levels`, `user-progress`, `task`;
- unit: вычисление статусов и переходов прогресса, если меняется модель состояния;
- component/browser: видимые тексты CTA, экранов и переходов между шагами;
- e2e smoke: сценарий «пользователь доводит решение до `Проверка пройдена`» без ощущения разорванного flow.

Команды проверки downstream change должны быть зафиксированы явно, минимум через `npm run test:traceability` и релевантные unit/browser/e2e команды.
