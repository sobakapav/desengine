## Why

Сейчас есть только один формат упаковки продукта — локальное развёртывание. Мы не знаем, какой формат «упаковки» действительно подойдёт пользователям, поэтому нужно расширять варианты.

Облачный доступ (hosted) важен, чтобы:

- снизить порог входа (без локальной установки);
- обеспечить доступ «с любого устройства»;
- упростить шаринг и быстрые демо;
- заложить основу для командного режима (в будущем).

## What Changes

Этот change описывает целевой формат упаковки «облачный доступ» и план реализации:

- целевой контур деплоя (hosted instance);
- модель хранения данных (проекты/задачи/артефакты) и границы ответственности клиента/сервера;
- требования к безопасности (аутентификация, изоляция данных, секреты);
- эксплуатационные требования (обновления, миграции, бэкапы, наблюдаемость);
- план тестирования (unit/integration/e2e smoke/live) и traceability.

## Non-goals

- Переписать продукт «под облако» целиком одним шагом.
- Выбор конкретного провайдера/облака как необратимое решение (на первом этапе).

## Capabilities

### New Capabilities (концептуально)
- `deployment-cloud`: запуск и использование продукта в облаке.

### Modified Capabilities
- `projects` / `dev-mode` (если включены): данные должны корректно жить в облачном хранилище и быть изолированы.

## Acceptance Criteria

- Зафиксирован целевой сценарий использования облачной версии (что умеет MVP, что позже).
- Определена граница между клиентом и сервером и минимальная модель данных.
- Есть roadmap на отдельные changes (аутентификация, storage, деплой, миграции и т.п.).
- Есть тестовый план и команды проверки для этапов реализации.
