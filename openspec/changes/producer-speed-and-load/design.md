## Контекст

- `focus-quality` уже держит стратегический фокус качества, проверяемости и устойчивости системы.
- В системе есть признаки утечек и неопределённой деградации скорости, но нет единого owner-контекста, который:
  - собирает симптомы;
  - формулирует допустимые профили нагрузки;
  - разводит исследование, измерение и исправление по downstream-веткам.
- Такие проблемы нельзя качественно вести только через `implement` или разовые `fix` changes: без общей рамки каждый следующий change заново спорит о том, что считать проблемой и как мерить улучшение.

## Goals

- Зафиксировать producer-owned рамку направления `speed-and-load`.
- Собрать минимальную карту проблем:
  - утечки;
  - деградации latency;
  - деградации под нагрузкой;
  - отсутствие понятных лимитов и guardrail'ов.
- Определить, какие метрики и профили нагрузки обязательны для обсуждения и приёмки.
- Подготовить почву для downstream `dispatcher` changes, которые уже будут организовывать конкретные delivery-работы.

## Non-goals

- Пытаться в этом change доказать все технические причины утечек.
- Устанавливать окончательные runtime-лимиты без данных.
- Делать кодовые оптимизации в обход downstream delivery-веток.

## Решение

- Создать `producer-speed-and-load` как отдельный producer под `focus-quality`.
- Вести внутри него собственный roadmap, который будет содержать:
  - подтверждённые симптомы;
  - гипотезы;
  - обязательные измерения;
  - целевые режимы нагрузки;
  - список downstream-направлений для dispatching.
- Рассматривать producer как owner вопросов:
  - что считать приемлемой скоростью;
  - какую нагрузку считать допустимой;
  - какие наблюдения уже достаточно надёжны, чтобы запускать downstream delivery.
- Передавать исполнение только через downstream `dispatcher` changes.

## Риски и компромиссы

- Если producer останется слишком абстрактным, он превратится в формальность без реальной пользы.
- Если producer начнёт формулировать слишком жёсткие цифры без измерений, downstream changes будут строиться на ложной точности.
- Если не развести уровни ответственности, producer начнёт подменять собой `dispatcher` и `implement`, чего делать нельзя.

## Открытые вопросы

- Какие именно симптомы утечек уже считаются подтверждёнными, а какие пока только подозреваются.
- Какие профили нагрузки для системы являются ключевыми в первую очередь: локальная разработка, preview/runtime, тестовый прогон, пользовательские сценарии.
- Какие текущие измерения уже есть в кодовой базе, а какие придётся вводить с нуля.
