## Контекст

- Родительский change управляет приоритетом и порядком реализации.
- Пользователь явно потребовал забыть legacy runtime как продуктовую сущность и вернуть работу на уровень проекта.

## Решение

1. Страница проекта становится главной рабочей поверхностью.
   Она больше не показывает legacy binding panel и не запускает работу через устаревший entry path.

2. Вводится project-owned session слой в canonical server-backed project storage.
   Этот слой хранит:
   - статус работы над проектом;
   - активные компонентные линии и workflow-сессии;
   - историю project-level событий;
   - наблюдаемую картину project workflow.

3. `ProjectComponent` остаётся частью проекта, а не отдельной точкой входа.
   Пользователь:
   - добавляет компонент в проект;
   - берёт его в работу внутри проекта;
   - видит его состояние внутри project workflow;
   - при необходимости возвращает его в активную линию работы проекта.

4. Project workflow становится explainability-слоем проекта.
   Он показывает:
   - этапы project-workflow;
   - активные линии работы;
   - положение каждого компонента внутри проектной работы.

5. Legacy index routes `/lab` и другие pre-project входы остаются только как redirect в `/projects`.

## Компромиссы

- В этом change legacy runtime не обязан исчезнуть из репозитория целиком.
  Он перестаёт быть user-facing и перестаёт определять project path; browser-local compatibility surface для project storage не сохраняется.
- Workbench не переизобретается как отдельный project page внутри этой волны.
  Вместо этого project page получает собственный project-first workspace layer.
