## Why

Старт уровня не должен падать только потому, что модель вернула `fileId` или имя файла вместо содержимого одного из обязательных рабочих файлов. Сейчас этот инвариант нарушен: если в initiator-ответе для `component` приходит строка `component` или `Component.tsx`, start-flow завершается ошибкой `Ответ вернул идентификатор вместо содержимого файла Component.tsx`.

На уровне 5 это проявляется особенно заметно, потому что старт требует несколько рабочих файлов, а новый render-template уже ожидает, что `Component.tsx` и связанные файлы будут сохранены как валидный рабочий набор.

## What Changes

- Добавить repair-path в start-flow для очевидного placeholder-ответа, когда модель возвращает `fileId` или `fileName` вместо содержимого файла.
- На этапе `normalizeStartPayload(...)` трактовать такой ответ как отсутствующее содержимое и подставлять:
  - текущее содержимое файла, если оно уже есть;
  - безопасный стартовый scaffold, если файла ещё нет.
- Распространить safe fallback как минимум на `Component.tsx` и `Component.stories.ts`, чтобы initiator-start не падал на обязательных файлах рабочего набора.
- Добавить unit-покрытие на нормализацию стартового payload и на защиту от file-id placeholders.

## Non-goals

- Не менять prompt contract или schema structured-output для start целиком.
- Не ослаблять validator для iterate/check.
- Не переписывать общий file-set или LLM strategy старта уровня.

## Impact

- Старт уровня перестанет падать на очевидном placeholder-ответе модели для обязательных файлов.
- Система сохранит валидный минимальный рабочий набор даже при частично испорченном start payload.
- Исправление останется локальным для initiator/start-flow и не изменит iterate/check semantics.
