## Context

Сейчас `lib/lab/sandpack-preview.ts` содержит крупные inline-шаблоны виртуального проекта Sandpack (HTML, TSX, конфиги). Логика сборки payload и сами шаблоны смешаны в одном файле.

## Goals / Non-Goals

**Goals:**
- Разнести шаблоны Sandpack preview по отдельным файлам на диске.
- Оставить текущий пользовательский результат (payload для Sandpack) без изменений.
- Сделать загрузку шаблонов предсказуемой в dev и production (Next.js build).
- Оставить безопасный fallback, чтобы отсутствие файлов не ломало preview.

**Non-Goals:**
- Изменение зависимостей Sandpack preview или переход на другой environment.
- Поддержка нескольких разных runtime-шаблонов (это может быть следующим шагом).
- Изменение действующих OpenSpec контрактов `task`/`level-labs` (в рамках этого change ожидаем только refactor+упаковку).

## Decisions

- Храним шаблоны в отдельном каталоге в репозитории (например `lib/lab/sandpack-templates/default/**`).
- Добавляем небольшую функцию-лоадер (например `loadSandpackDefaultTemplate()`), которая:
  - читает файлы с диска;
  - кэширует результат в памяти процесса (чтобы не читать на каждый запрос);
  - умеет отдавать fallback (встроенные значения), если файл не найден или чтение упало.
- Для production фиксируем явное включение каталога шаблонов в build output Next.js (через `next.config.ts` file tracing includes или альтернативный способ упаковки).

## Risks / Trade-offs

- [File tracing] Next.js может не включить произвольные файлы, читаемые через `fs`, в production bundle → нужна явная настройка включения или гарантированное расположение шаблонов.
- [Дрейф шаблонов] при наличии fallback можно случайно не заметить, что шаблоны не подхватились → стоит добавить unit-проверку, что в тестовом окружении шаблоны читаются с диска (и/или логировать деградацию в dev).
- [Кэширование] кэш ускоряет, но в dev может мешать быстрым правкам шаблонов → в dev-режиме можно отключить кэш или сбрасывать его при HMR.
