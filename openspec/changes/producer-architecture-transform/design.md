## Context

В проекте уже есть много сильных архитектурных наработок, но они пока воспринимаются либо как локальные технические решения, либо как разрозненные product/runtime линии. При этом текущее понимание системы уже требует более собранной карты:

- есть верхний лейтмотив `AI-трансформации`;
- есть сквозные бизнес-аттракторы: `код`, `LLM`, `бюджет`, `дизайн`;
- есть рабочая динамика `проект -> задача -> процесс -> шаг -> верстак -> инструмент`;
- есть слои: организационный, рабочее место, реализация, экспертность, системный.
- `AI-трансформация` не равна onboarding и не должна насильно превращаться в ещё одну сущность;
- `сессия работы` пока не выделяется в отдельный слой и считается частью `рабочего места`;
- `верстак` и `шаг` не считаются отношением `1:1`: один верстак может держать несколько шагов или фрагмент процесса;
- `документация` и `Figma` важны, но пока не поднимаются до отдельного списка сквозных сущностей:
  - документация остаётся опорой организационного слоя;
  - Figma остаётся важной внешней рабочей средой;
- `качество` не включается в список сквозных сущностей и не должно размывать текущую бизнесовую четвёрку.

Producer нужен для того, чтобы эта карта не осталась разовой мыслительной конструкцией, а стала управляющей рамкой для будущих changes.

## Goals

- Зафиксировать архитектурную трансформацию как продюсерскую линию с пользовательским эффектом.
- Передать producer явный implementation plan, из которого можно порождать dispatcher и implement/fix waves.
- Удержать согласованность между:
  - архитектурной картой;
  - ADR;
  - именованием в коде;
  - downstream technical ownership.

## Non-goals

- Не описывать детальный low-level refactor каждого модуля.
- Не определять окончательный package/folder layout всей кодовой базы.
- Не превращать producer в единственного исполнителя всей архитектурной работы.

## Decisions

1. Архитектурная трансформация оформляется именно как producer-line.
   Это оправдано тем, что уже первые изменения этой линии меняют пользовательский опыт, а не только внутреннее устройство кода.

2. Producer держит не реализацию, а управляющую рамку:
   - архитектурную карту;
   - implementation plan;
   - правила ADR;
   - правила модульных границ;
   - правила именования.
   Producer обязан удерживать эту рамку в бизнес-читаемом виде и не подменять `AI-трансформацию` частными механизмами вроде onboarding или локального UX-улучшения.

3. Tactical ownership выносится в `dispatcher-architecture`.
   Producer не делает всё сам, а порождает и направляет downstream waves.

4. Не все элементы карты автоматически становятся самостоятельными dispatcher-lines.
   Dispatcher создаются только там, где есть живая архитектурная линия с собственным backlog и риском расползания.

5. Код и LLM признаются сквозными сущностями этой линии, но не оформляются как новые слои.
   Downstream implementation waves должны проявлять их как самостоятельные архитектурные контуры внутри уже существующей слоистой карты.

## Implementation Plan

### Шаг 1. Зафиксировать архитектуру как управляемую карту

- создать `dispatcher-architecture`;
- закрепить в ADR и живой документации:
  - архитектурную карту;
  - словарь сущностей;
  - правила именования;
  - принцип «важная сущность должна иметь явное место в коде»;
  - ограничение текущего списка сквозных сущностей;
  - роль `AI-трансформации` как vision-обещания, а не как отдельного operational-модуля.

### Шаг 2. Выделить tactical ownership архитектурной линии

- передать `dispatcher-architecture` ответственность за:
  - operational backlog;
  - развитие ADR;
  - контроль реализации архитектурной карты;
  - маршрутизацию downstream changes.

### Шаг 3. Породить первые implementation waves

Первые downstream changes должны сосредоточиться на темах, уже видимых в коде:

- укрепление границ рабочего места;
- выделение понятных модулей для работы с кодом;
- выделение понятных модулей для работы с LLM;
- усиление архитектурного именования;
- явные контракты общения между крупными частями системы.

Эти changes не должны:

- раздувать список сквозных сущностей без отдельного producer-решения;
- насильно отделять `сессию работы` от `рабочего места`, пока на это нет отдельного архитектурного решения;
- фиксировать жёсткое соответствие `один шаг = один верстак`.

### Шаг 4. Привязать changes к проверяемой дисциплине

Каждый downstream behavior-change этой линии обязан:

- ссылаться на producer и соответствующий dispatcher;
- обновлять ADR/карту там, где меняется архитектурная граница;
- явно показывать verification layer;
- не вводить анонимные архитектурные сущности без словаря и именования.

## Risks / Trade-offs

- [Риск] Producer станет слишком абстрактным и оторвётся от кода.
  -> Mitigation: держать в producer только те architectural promises, которые потом можно ткнуть пальцем в downstream changes и коде.

- [Риск] Dispatcher превратится в свалку всего важного в кодовой базе.
  -> Mitigation: ограничить `dispatcher-architecture` только архитектурной картой, ADR, модульными границами и именованием.

- [Риск] Архитектурная карта будет спорить с фактической реализацией.
  -> Mitigation: считать producer и dispatcher местом синхронизации карты и кода, а не декоративной документацией.

## Open Questions

- Нужен ли отдельный downstream dispatcher для сквозной линии работы с кодом после первичной стабилизации `dispatcher-architecture`.
- Нужен ли отдельный downstream dispatcher для линии работы с LLM после первичной стабилизации `dispatcher-architecture`.
