## Context

Сейчас система умеет проверять результат, но не обязана объяснять, какие именно изменения сделали решение правильным. Для обучающего продукта это потеря ценности: человек проходит задачу, но не получает сжатую обратную связь о сути победы.

## Goals

- Реализовать didactic feedback после успеха.
- Встроить его в текущий check-result flow без раскрытия полного готового ответа.

## Non-goals

- Не превращать этот change в механизм полного просмотра reference solution.
- Не переписывать весь pipeline проверки ради одной UX-функции.

## Decisions

1. Жалоба переводится в `implement`, а не остаётся на уровне идеи.
2. Реализация живёт под `dispatcher-ux`, потому что это вопрос качества обратной связи и восприятия результата.
3. Первый implementation-pass может быть проще идеального semantic diff, если он уже даёт человеку понятный ответ “что изменилось”.

## Risks

- Неосторожная реализация может превратить обучение в «посмотри готовый ответ».
- Diff без контекста может оказаться шумным и не более полезным, чем текущее состояние.

## Open Questions

- Нужно ли показывать structural diff, semantic summary или оба слоя.
- Должен ли такой feedback появляться всегда или только по запросу пользователя.
