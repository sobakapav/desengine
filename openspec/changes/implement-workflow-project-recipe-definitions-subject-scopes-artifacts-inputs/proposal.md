## Why

Текущий `workflow` в системе слишком узок для следующего продуктового шага.

Сейчас он по сути выражает один project-owned recipe:

- один `workflowKind` у компонента;
- одну project session;
- один набор жёстко зашитых стадий;
- readout, который больше объясняет происходящее, чем управляет разными видами работы.

Этого достаточно для короткой цепочки `проект -> компонент -> работа`, но недостаточно для реальной линейки workflow, которая уже нужна продукту:

- создание компонента по изображению или Figma;
- композиция экранов;
- генерация mock-данных;
- Storybook и documentation;
- migration между UI kit;
- работа с доменной моделью;
- extraction/refactor/import flows.

Проблема не в том, что “не хватает ещё пары workflow”. Проблема в самой модели `workflow`: она пока не умеет быть каталогом проектных операций над разными предметами работы.

## What Changes

- Ввести workflow как каталог reusable проектных операций, а не как один жёсткий process recipe.
- Зафиксировать архитектурную модель:
  - `WorkflowDefinition` как шаблон операции;
  - `WorkflowRun` как конкретный запуск внутри проекта;
  - `WorkflowSubject` как указание, над чем идёт работа;
  - `WorkflowTemplateBinding` как project-level выбор доступных шаблонов;
  - typed `artifact slots`, `input contracts` и `output contracts`.
- Развести разные уровни workflow:
  - catalog level;
  - project configuration level;
  - runtime run level;
  - user-facing launch surfaces.
- Подготовить систему к семействам workflow над:
  - компонентами;
  - наборами компонентов;
  - экранами;
  - данными;
  - Storybook;
  - доменной моделью;
  - миграцией UI kit / design system;
  - системным extraction / refactor.
- Зафиксировать список референсных workflow-примеров как отдельный продуктовый артефакт.

## Impact

- Workflow перестаёт быть привязан только к одному component recipe.
- Project surface получает шанс в будущем запускать разные workflow из разных контекстов, а не только “работу над текущим компонентом”.
- Artifact, PromptContext и project boundaries получают более честную опору, потому что знают не только шаг, но и тип операции, предмет работы и ожидаемые результаты.
- Появляется архитектурное место для данных и доменной модели внутри продукта.
