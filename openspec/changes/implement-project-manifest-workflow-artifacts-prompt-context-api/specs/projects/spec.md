## MODIFIED Requirements

### Requirement: Проект имеет простой пользовательский config surface

Система SHALL давать пользователю простой способ прочитать и изменить конфигурацию проекта на странице `/projects/<projectId>` через явные пользовательские поля.

#### Scenario: Пользователь открывает config проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает project config как самостоятельный пользовательский surface
- **AND** config читается из canonical `ProjectWorkspace`

#### Scenario: Пользователь редактирует title и id проекта
- **WHEN** пользователь меняет название или идентификатор проекта
- **THEN** система сохраняет обновлённый `ProjectWorkspace`
- **AND** не оставляет в registry вторую stale-версию этого же проекта под старым `id`

#### Scenario: Пользователь меняет UI kit проекта из canonical списка
- **WHEN** пользователь выбирает другой `uiKitId` для проекта
- **THEN** система использует canonical список доступных UI kit'ов
- **AND** изменение сохраняется в `ProjectWorkspace.settings`
- **AND** пользователь видит только один выбранный UI kit без отдельного effective-режима

#### Scenario: Пользователь видит, где хранится проект
- **WHEN** пользователь просматривает конфигурацию проекта
- **THEN** система явно сообщает, что проект хранится на диске машины сервера
- **AND** показывает canonical server path проекта

#### Scenario: Пользователь экспортирует и импортирует manifest проекта
- **WHEN** пользователь работает на странице проекта
- **THEN** project surface позволяет выгрузить manifest проекта и загрузить manifest обратно
- **AND** эти действия читаются как часть владения проектом, а не как служебная debug-операция

### Requirement: Проект показывает workflow как наблюдаемый слой

Система SHALL позволять пользователю видеть project-owned workflow как часть страницы проекта, даже если управление им пока остаётся read-only.

#### Scenario: Пользователь открывает workflow проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает workflow проекта как самостоятельную наблюдаемую сущность
- **AND** пользователь видит шаги project-workflow, активные линии работы и последнюю активность
- **AND** система объясняет связь workflow с проектом и его компонентами, а не с отдельной legacy-сущностью

#### Scenario: Пользователь видит выбранный workflow template проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** проектная поверхность явно показывает, какой workflow template сейчас направляет работу
- **AND** template читается как reusable recipe, а не как скрытая внутренняя настройка

## ADDED Requirements

### Requirement: Проект показывает artifact library как часть рабочей поверхности

Система SHALL показывать на странице проекта явную библиотеку project-owned материалов работы.

#### Scenario: Пользователь открывает artifact library проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает artifacts проекта как отдельный пользовательский слой
- **AND** artifacts читаются как материалы проектной работы, а не как случайные внутренние следы runtime

### Requirement: Проект показывает prompt brief как редактируемый рабочий бриф

Система SHALL давать пользователю project-facing prompt brief как управляемый рабочий бриф проекта.

#### Scenario: Пользователь читает prompt brief проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает brief, который влияет на prompt context
- **AND** brief объясняет, что именно проект хочет получить от workflow и LLM-контуров
