## Context

Сейчас `/help` — серверная страница с зашитым списком карточек. В проекте уже есть `MarkdownContent`, который умеет рендерить Markdown, относительные ссылки и Mermaid code fences, и есть `MermaidDiagram` для отдельного рендера диаграмм. Доступ к текущей `/help` проверяется на уровне route-файла через `requireAccessOrRedirect`.

Новая справка должна остаться частью защищённого product-shell, но контент должен переехать в корневой каталог `help/`, чтобы документацию можно было править без изменения React-компонентов.

## Goals / Non-Goals

**Goals:**

- Читать Markdown-страницы из `help/*.md` и строить каталог `/help` по их H1.
- Рендерить `/help/[helpId]` через `MarkdownContent`.
- Отдавать отдельный управляемый экран `/help/error` для ошибок help-контента.
- Отдавать картинки из `help/images/*` по `/help/images/[imgId]`.
- Рендерить Mermaid-исходники из `help/mermaid/*` по `/help/mermaid/[mermaidId]`.
- Сохранить route-level access guard для всех пользовательских help entry points.
- Добавить понятное покрытие в общий слой тестирования.

**Non-Goals:**

- Не добавлять CMS, фронтматтер, поиск, теги или ручную сортировку.
- Не менять `MarkdownContent`, если хватает существующего `assetBasePath`.
- Не менять Node.js, Next.js, Turbopack или install-critical стек.
- Не поддерживать вложенные help-страницы глубже одного URL-сегмента.

## Decisions

1. Файловый слой живёт в `lib/help/content.ts`.
   - Причина: route-файлы остаются тонкими, а unit-тесты могут проверять парсинг H1, сортировку и безопасность path traversal без запуска Next.
   - Альтернатива: читать файлы прямо в `app/help/**`; это быстрее написать, но сложнее тестировать и легче размазать правила безопасности.

2. Help ID ограничивается безопасным одно-сегментным идентификатором.
   - `helpId` мапится в `help/<helpId>.md`.
   - `imgId` мапится в `help/images/<imgId>`.
   - `mermaidId` мапится в `help/mermaid/<mermaidId>.mmd`, при этом URL может передать идентификатор без расширения.
   - Причина: исключить `..`, скрытые файлы и вложенные пути.

3. Каталог `/help` сортируется по отображаемому заголовку.
   - Заголовок берётся из первого Markdown H1.
   - Если H1 отсутствует, используется имя файла без `.md`.
   - Причина: пользователь видит содержательную навигацию, а контент без H1 остаётся доступным.

4. Ошибки help-страниц ведут на `/help/error`.
   - Для пользовательских страниц используется отдельный route, а не стандартный `notFound()`.
   - Для binary assets route handler возвращает HTTP-ошибку, потому что браузер запрашивает их как ресурсы, а не как HTML-страницы.

5. Относительные assets внутри Markdown используют `assetBasePath="/help"`.
   - `![alt](images/example.png)` превращается в `/help/images/example.png`.
   - Ссылки на Mermaid-страницы можно писать как `[Диаграмма](mermaid/example)`.

## Risks / Trade-offs

- [Risk] Картинка без расширения не получит точный MIME type → route handler вернёт `application/octet-stream`; для пользовательских картинок в примерах используем расширения.
- [Risk] Mermaid-URL с расширением и без расширения могут быть использованы непоследовательно → поддерживаем оба варианта, но канонические ссылки в документации пишем без `.mmd`.
- [Risk] Защищённые картинки внутри Markdown могут не отобразиться при истёкшей сессии → route handler вернёт `401`, а сама страница при обновлении вернёт пользователя в auth-flow.
