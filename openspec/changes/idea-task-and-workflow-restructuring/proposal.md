## Why

Пользователь приходит в desengine с разными типами задач:

1) проработать конкретный компонент до Storybook-состояния;  
2) создать дизайн-систему (компоненты/токены/лейауты/иконки);  
3) декомпозировать внешний «вайбкод» в набор компонентов;  
4) собрать сложный компонент из простых;  
5) собрать прототип продукта/интерфейса с нуля.

У каждой задачи есть:

- **стартовые артефакты** (что уже дано и чем можно пользоваться);
- **workflow** (путь к результату, где шаги могут быть очень разными и эволюционировать);
- **нюансы/ограничения** (контекст, зависимости, качество, тесты, дизайн-ограничения).

Сейчас задачи разных типов слишком легко смешиваются в один общий поток. Из-за этого системе трудно ясно понимать:

- какой тип запроса перед ней;
- какие артефакты должны быть стартовыми именно для этого запроса;
- какой workflow подходит этому типу работы;
- где одна форма задачи уже должна перерастать в другую.

Нужна не просто “модель сущностей”, а идея о том, как **реструктурировать задачи и workflow под разные типы запросов**, чтобы система масштабировалась без смешения режимов работы.

## What Changes

Этот change — idea-уровня: он фиксирует смысловую рамку будущей реструктуризации задач и workflow.

Результаты должны включать:

- идею новой структуры задач для разных типов запросов;
- типологию задач (минимум 5 классов выше) и их стартовые артефакты;
- представление о том, как workflow должен зависеть от типа задачи;
- развилки и открытые вопросы, которые потом можно будет перевести в producer/dispatcher changes;
- тестовую и traceability-рамку для будущих behavior-change changes.

## Non-goals

- Реализация полной системы Task/Workflow «до конца» в рамках этого change.
- Жёсткое предопределение всех шагов workflow: шаги должны быть расширяемыми.
- Преждевременное превращение этой темы в delivery-план, пока не собрана правильная идея реструктуризации.

## Capabilities

### New Capabilities
- `workflow`: исполнение и управление workflow-ами.
- `task-model`: доменная сущность Task как контейнер артефактов и целей.

### Modified Capabilities
- `task` (если уже есть текущая сущность/экран): будет уточнён контракт и границы ответственности.
- `projects` / `dev-mode` (если включены): Task и Workflow должны быть project-scoped.

## Acceptance Criteria

- В change есть ясная идея, как разводить разные типы запросов по разным task/workflow-контурам.
- Описаны как минимум 5 типов задач и их стартовые артефакты.
- Понятно, какие части темы потом должны стать отдельными producer или dispatcher changes.
- Есть тестовая и traceability-рамка для будущих behavior-change changes.
