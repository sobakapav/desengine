## Requirements

### Requirement: Project Workspace является canonical project scope

Система SHALL иметь единую сущность `ProjectWorkspace` для настроек и данных проекта.

#### Scenario: Пользователь создаёт первый проект в MVP workspace
- **WHEN** в registry ещё нет ни одного проекта
- **AND** пользователь создаёт первый `ProjectWorkspace` с именем и абсолютным server path
- **THEN** система сохраняет canonical `ProjectWorkspace` с `id`, `title`, `createdAt`, `updatedAt` и `settings`
- **AND** в `ProjectWorkspace.settings` сразу фиксируется базовый `uiKitId`
- **AND** этот проект становится active project через project boundary

#### Scenario: Пользователь подключает существующий проект с диска
- **WHEN** пользователь указывает server path каталога, где уже лежит desengine project
- **THEN** система читает canonical project files из этого каталога
- **AND** добавляет проект в project registry
- **AND** позволяет открыть этот проект через обычный project path

#### Scenario: Пользователь открывает рабочую среду в активном проекте
- **WHEN** пользователь открывает рабочую среду продукта
- **THEN** runtime определяет active project через project boundary
- **AND** настройки preview берутся из `ProjectWorkspace.settings`

#### Scenario: Пользователь переключает active project через project registry
- **WHEN** в registry доступно несколько `ProjectWorkspace`
- **AND** пользователь выбирает другой проект
- **THEN** project boundary сохраняет новый active project
- **AND** workflow и preview читают уже выбранный `ProjectWorkspace`, а не локальный fallback старого обходного слоя

#### Scenario: Настройки preview сохраняются в project settings
- **WHEN** пользователь меняет `uiKitId`
- **THEN** изменение сохраняется как настройка `ProjectWorkspace.settings`
- **AND** Workbench не создаёт отдельный несовместимый Project shape

#### Scenario: Runtime записывает product event через единую project boundary
- **WHEN** project runtime передаёт валидный `EventEnvelope` в boundary записи события
- **THEN** boundary принимает только foundation contract `EventEnvelope`
- **AND** по умолчанию использует один `stub/no-op` sink без storage

### Requirement: Проекты доступны как самостоятельный пользовательский раздел

Система SHALL показывать проекты в глобальной навигации и открывать их через отдельный route-слой как каноническую точку входа в работу.

#### Scenario: Пользователь видит вкладку проектов в верхнем меню
- **WHEN** пользователь открывает любой основной экран продукта
- **THEN** в глобальной навигации есть вкладка `Проекты`
- **AND** она ведёт в canonical раздел `/projects`

#### Scenario: Пользователь открывает список проектов
- **WHEN** пользователь переходит в `/projects`
- **THEN** система показывает список проектов из canonical project registry
- **AND** отдельно отмечает active project

#### Scenario: Пользователь создаёт новый проект из project registry
- **WHEN** пользователь открывает `/projects`
- **AND** вводит имя нового проекта и абсолютный server path
- **THEN** система создаёт новый `ProjectWorkspace` в canonical project registry
- **AND** пользователь сразу видит этот проект в списке раздела `Проекты`

#### Scenario: Пользователь открывает страницу конкретного проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает project overview для этого `ProjectWorkspace`
- **AND** не требует предварительно заходить в другой промежуточный рабочий экран

### Requirement: Страница проекта является главной рабочей поверхностью

Система SHALL строить работу вокруг страницы проекта как главной пользовательской поверхности продукта.

#### Scenario: Пользователь открывает страницу проекта и попадает в рабочий контур проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает явный project-workflow, активные линии работы и историю работы прямо на странице проекта
- **AND** пользователю не требуется отдельный промежуточный экран, чтобы понять, чем сейчас занят проект

#### Scenario: Страница проекта выделяет один главный следующий шаг
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** project page показывает один главный next action в верхней части экрана
- **AND** этот next action ведёт пользователя по цепочке `создать компонент -> запустить линию работы -> продолжить работу`
- **AND** config, подробный workflow и история остаются доступными как вторичный supporting слой, а не как центр внимания

#### Scenario: Неподходящий старый маршрут больше не конкурирует с project path
- **WHEN** пользователь попадает в старый маршрут, который не должен быть рабочим входом проекта
- **THEN** система возвращает его в canonical project path
- **AND** project page остаётся единственной главной поверхностью работы

#### Scenario: Страница проекта делает верстак прощупываемым без допуска к работе
- **WHEN** у проекта materialized workbench shell уже доступен
- **THEN** project page показывает этот shell как часть проектной поверхности
- **AND** пользователь может открыть shell из проекта
- **AND** проектная страница остаётся главным местом управления работой, пока верстак ещё locked

### Requirement: Проект является контейнером для пользовательских компонентов

Система SHALL показывать на странице проекта его компоненты как отдельные project-scoped сущности, которые входят в общую работу над проектом.

#### Scenario: Пользователь видит список компонентов проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает список компонентов, принадлежащих этому проекту
- **AND** компонент читается как самостоятельная project-scoped сущность внутри проекта

#### Scenario: Пользователь создаёт компонент внутри проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **AND** вводит имя нового компонента
- **THEN** система создаёт `ProjectComponent`, связанный с этим `ProjectWorkspace`
- **AND** по умолчанию фиксирует для него workflow `image-to-component-workflow`
- **AND** новый компонент сразу появляется в списке компонентов проекта
- **AND** создание компонента само по себе не запускает отдельную побочную рабочую сущность

#### Scenario: Пользователь запускает работу по компоненту проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **AND** в проекте уже создан `ProjectComponent`
- **THEN** карточка компонента показывает действие `Взять в работу`
- **AND** project page запускает рабочую линию по этому компоненту прямо внутри project surface
- **AND** пользователь видит это изменение прямо в project surface

#### Scenario: Компонент не открывает отдельную runtime-сессию
- **WHEN** пользователь запускает рабочую линию по компоненту
- **THEN** система трактует этот компонент как активную часть общей проектной работы
- **AND** не требует отдельного служебного идентификатора как пользовательской сущности
- **AND** не переводит пользователя на другой рабочий маршрут

#### Scenario: Пользователь видит положение компонента внутри project-workflow
- **WHEN** у проекта уже есть рабочая сессия и одна или несколько активных линий
- **THEN** карточка компонента показывает, запущена ли по нему активная работа проекта
- **AND** отдельно показывает последнюю активность и положение внутри общей проектной работы
- **AND** пользователь может вернуть готовый компонент обратно в активную работу проекта, не выходя со страницы проекта

#### Scenario: Пользователь отмечает компонент как готовый внутри проекта
- **WHEN** пользователь завершает работу над компонентом
- **THEN** проектная страница позволяет отметить компонент как готовый
- **AND** этот статус сохраняется как часть project-level работы
- **AND** пользователь наблюдает итог прямо в project surface

### Requirement: Проект имеет простой пользовательский config surface

Система SHALL давать пользователю простой способ прочитать и изменить конфигурацию проекта на странице `/projects/<projectId>` через явные пользовательские поля.

#### Scenario: Пользователь открывает config проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает project config как самостоятельный пользовательский surface
- **AND** config читается из canonical `ProjectWorkspace`

#### Scenario: Пользователь редактирует title и id проекта
- **WHEN** пользователь меняет название или идентификатор проекта
- **THEN** система сохраняет обновлённый `ProjectWorkspace`
- **AND** не оставляет в registry вторую stale-версию этого же проекта под старым `id`

#### Scenario: Пользователь меняет UI kit проекта из canonical списка
- **WHEN** пользователь выбирает другой `uiKitId` для проекта
- **THEN** система использует canonical список доступных UI kit'ов
- **AND** этот список берётся из реестра системных `UI kit adapter`
- **AND** изменение сохраняется в `ProjectWorkspace.settings`
- **AND** пользователь видит только один выбранный UI kit без отдельного effective-режима

#### Scenario: Пользователь управляет UI kit в верхнем слое страницы проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает явный верхний control управления UI kit проекта
- **AND** этот control объясняет, что поддержанные UI kit'ы поставляются внутри desengine
- **AND** не требует от пользователя вручную ставить зависимости kit'а

#### Scenario: Пользователь видит, где хранится проект
- **WHEN** пользователь просматривает конфигурацию проекта
- **THEN** система явно показывает, что проект хранится на диске машины сервера
- **AND** показывает реальный canonical server path проекта

#### Scenario: Изменения проекта сохраняются автоматически
- **WHEN** пользователь меняет project-facing данные или рабочее состояние проекта
- **THEN** система сохраняет canonical project state на диск фоном-автоматом
- **AND** не требует общего ручного действия "сохранить проект" для фиксации состояния

#### Scenario: Пользователь экспортирует и импортирует manifest проекта
- **WHEN** пользователь работает на странице проекта
- **THEN** project surface позволяет выгрузить manifest проекта и загрузить manifest обратно
- **AND** эти действия читаются как часть владения проектом, а не как служебная debug-операция

### Requirement: Проект показывает свою историю и диагностику

Система SHALL показывать пользователю project-scoped историю самой работы над проектом: старт работы, запуск линий по компонентам и переход компонентов в готовый слой.

#### Scenario: Пользователь открывает историю проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает последовательность project-level событий
- **AND** пользователь видит, какие компоненты добавлялись, какие линии по ним запускались и что уже отмечено как готовое

#### Scenario: Пользователь видит последнюю project-level активность
- **WHEN** у проекта уже есть история работы
- **THEN** project surface показывает последнюю активность как часть диагностики проекта
- **AND** эта активность читается как часть работы над проектом

### Requirement: Проект показывает workflow как наблюдаемый слой

Система SHALL позволять пользователю видеть project-owned workflow как часть страницы проекта, даже если управление им пока остаётся read-only.

#### Scenario: Пользователь открывает workflow проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает workflow проекта как самостоятельную наблюдаемую сущность
- **AND** пользователь видит шаги project-workflow, активные линии работы и последнюю активность
- **AND** система объясняет связь workflow с проектом и его компонентами

#### Scenario: Пользователь видит выбранный workflow template проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** проектная поверхность явно показывает, какой workflow template сейчас направляет работу
- **AND** template читается как reusable recipe, а не как скрытая внутренняя настройка

### Requirement: Проект показывает artifact library как часть рабочей поверхности

Система SHALL показывать на странице проекта явную библиотеку project-owned материалов работы.

#### Scenario: Пользователь открывает artifact library проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает artifacts проекта как отдельный пользовательский слой
- **AND** artifacts читаются как материалы проектной работы, а не как случайные внутренние следы runtime

### Requirement: Проект показывает prompt brief как редактируемый рабочий бриф

Система SHALL давать пользователю project-facing prompt brief как управляемый рабочий бриф проекта.

#### Scenario: Пользователь читает prompt brief проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает brief, который влияет на prompt context
- **AND** brief объясняет, что именно проект хочет получить от workflow и LLM-контуров
