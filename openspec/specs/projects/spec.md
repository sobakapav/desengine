## Requirements

### Requirement: Project Workspace является canonical project scope

Система SHALL иметь единую сущность `ProjectWorkspace` для настроек и данных проекта.

#### Scenario: Пользователь создаёт первый проект в MVP workspace
- **WHEN** в registry ещё нет ни одного проекта
- **AND** пользователь создаёт первый `ProjectWorkspace` с именем
- **THEN** система сохраняет canonical `ProjectWorkspace` с `id`, `title`, `createdAt`, `updatedAt` и `settings`
- **AND** в `ProjectWorkspace.settings` сразу фиксируется базовый `uiKitId`
- **AND** этот проект становится active project через project boundary

#### Scenario: Пользователь открывает lab в активном проекте
- **WHEN** пользователь открывает лабораторию
- **THEN** runtime определяет active project через project boundary
- **AND** настройки preview берутся из `ProjectWorkspace.settings`

#### Scenario: Пользователь переключает active project через project registry
- **WHEN** в registry доступно несколько `ProjectWorkspace`
- **AND** пользователь выбирает другой проект
- **THEN** project boundary сохраняет новый active project
- **AND** лаборатория и preview читают уже выбранный `ProjectWorkspace`, а не task-local fallback

#### Scenario: Настройки preview сохраняются в project settings
- **WHEN** пользователь меняет `uiKitId`
- **THEN** изменение сохраняется как настройка `ProjectWorkspace.settings`
- **AND** Workbench не создаёт отдельный несовместимый Project shape

#### Scenario: Runtime записывает product event через единую project boundary
- **WHEN** project runtime передаёт валидный `EventEnvelope` в boundary записи события
- **THEN** boundary принимает только foundation contract `EventEnvelope`
- **AND** по умолчанию использует один `stub/no-op` sink без storage

### Requirement: Проекты доступны как самостоятельный пользовательский раздел

Система SHALL показывать проекты в глобальной навигации и открывать их через отдельный route-слой, а не только изнутри Workbench конкретной задачи.

#### Scenario: Пользователь видит вкладку проектов в верхнем меню
- **WHEN** пользователь открывает любой основной экран продукта
- **THEN** в глобальной навигации есть вкладка `Проекты`
- **AND** она ведёт в canonical раздел `/projects`

#### Scenario: Пользователь открывает список проектов
- **WHEN** пользователь переходит в `/projects`
- **THEN** система показывает список проектов из canonical project registry
- **AND** отдельно отмечает active project

#### Scenario: Пользователь создаёт новый проект из project registry
- **WHEN** пользователь открывает `/projects`
- **AND** вводит имя нового проекта
- **THEN** система создаёт новый `ProjectWorkspace` в canonical project registry
- **AND** пользователь сразу видит этот проект в списке раздела `Проекты`

#### Scenario: Пользователь открывает страницу конкретного проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает project overview для этого `ProjectWorkspace`
- **AND** не требует предварительно заходить в Workbench конкретной задачи

### Requirement: Страница проекта показывает связанные задачи

Система SHALL показывать на странице проекта задачи, уже связанные с этим project context, чтобы проект читался как рабочий контейнер, а не как абстрактная настройка.

#### Scenario: Пользователь открывает страницу проекта и видит его задачи
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает список задач, связанных с этим проектом
- **AND** пользователь может перейти из проекта в связанную задачу

### Requirement: Проект является контейнером для пользовательских компонентов

Система SHALL показывать на странице проекта его компоненты как отдельные project-scoped сущности, из которых затем может стартовать и продолжаться workflow-работа.

#### Scenario: Пользователь видит список компонентов проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **THEN** система показывает список компонентов, принадлежащих этому проекту
- **AND** компонент читается как самостоятельная project-scoped сущность, а не как скрытый хвост task runtime

#### Scenario: Пользователь создаёт компонент внутри проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **AND** вводит имя нового компонента
- **THEN** система создаёт `ProjectComponent`, связанный с этим `ProjectWorkspace`
- **AND** по умолчанию фиксирует для него workflow `image-to-component-workflow`
- **AND** новый компонент сразу появляется в списке компонентов проекта
- **AND** создание компонента само по себе не запускает workflow-сессию

#### Scenario: Пользователь начинает работу над компонентом проекта
- **WHEN** пользователь открывает `/projects/<projectId>`
- **AND** в проекте уже создан `ProjectComponent`
- **THEN** карточка компонента показывает действие `Работать над компонентом`
- **AND** пользователь может открыть реальную workflow-сессию этого компонента без ручного поиска backing task

#### Scenario: Компонент проекта сохраняет связь с backing task
- **WHEN** пользователь впервые запускает workflow из `ProjectComponent`
- **THEN** система сохраняет `backing taskId` внутри сущности компонента
- **AND** при повторном входе пользователь возвращается в ту же workflow-сессию компонента

#### Scenario: Пользователь видит состояние workflow-сессии прямо в карточке компонента проекта
- **WHEN** у `ProjectComponent` уже есть назначенный `backing task`
- **AND** project page уже получила workflow readout для этого task
- **THEN** карточка компонента показывает статус workflow-run
- **AND** отдельно показывает последнюю активность и краткий прогресс по пунктам workflow
- **AND** главное действие карточки переключается на `Продолжить работу`

#### Scenario: Пользователь видит компонент проекта на экране задачи
- **WHEN** пользователь открывает task surface для backing task компонента проекта
- **THEN** экран задачи показывает, что task связан не только с проектом, но и с конкретным `ProjectComponent`

#### Scenario: Пользователь видит компонент проекта в списке задач
- **WHEN** task уже используется как backing runtime компонента проекта
- **THEN** карточка задачи показывает название этого `ProjectComponent`
- **AND** пользователь не путает разные workflow-сессии только по `taskId`

### Requirement: Проект имеет простой пользовательский config surface

Система SHALL давать пользователю простой способ прочитать и изменить конфигурацию проекта на странице `/projects/<projectId>` через явные пользовательские поля.

#### Scenario: Пользователь открывает config проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает project config как самостоятельный пользовательский surface
- **AND** config читается из canonical `ProjectWorkspace`

#### Scenario: Пользователь редактирует title и id проекта
- **WHEN** пользователь меняет название или идентификатор проекта
- **THEN** система сохраняет обновлённый `ProjectWorkspace`
- **AND** не оставляет в registry вторую stale-версию этого же проекта под старым `id`

#### Scenario: Пользователь меняет UI kit проекта из canonical списка
- **WHEN** пользователь выбирает другой `uiKitId` для проекта
- **THEN** система использует canonical список доступных UI kit'ов
- **AND** изменение сохраняется в `ProjectWorkspace.settings`
- **AND** пользователь видит только один выбранный UI kit без отдельного effective-режима

#### Scenario: Пользователь видит, где хранится проект
- **WHEN** пользователь просматривает конфигурацию проекта
- **THEN** система явно сообщает, что проект пока хранится локально в браузере
- **AND** не показывает вымышленный файловый path

### Requirement: Проект показывает свою историю и диагностику

Система SHALL показывать пользователю project-scoped историю и diagnostics, уже накопленные внутри canonical runtime проекта.

#### Scenario: Пользователь открывает историю проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает project-scoped историю работы
- **AND** история опирается на canonical runtime данные проекта

#### Scenario: Пользователь видит reset след проекта
- **WHEN** у проекта есть reset-related след
- **THEN** система показывает это как часть диагностики проекта
- **AND** не прячет важные последствия project-level изменений

### Requirement: Проект показывает workflow как наблюдаемый слой

Система SHALL позволять пользователю видеть project-aware workflow как часть страницы проекта, даже если управление workflow пока остаётся read-only.

#### Scenario: Пользователь открывает workflow проекта
- **WHEN** пользователь открывает страницу проекта
- **THEN** система показывает workflow-run проекта как самостоятельную наблюдаемую сущность
- **AND** пользователь видит статус run, пункты workflow и последнюю активность
- **AND** система объясняет связь workflow с задачей и Workbench
