## Requirements
### Requirement: Экспортируемые сущности документированы для человека
Система разработки SHALL требовать понятные комментарии для экспортируемых функций, типов и констант, а также для нетривиальных файлов, чтобы разработчик мог понять намерение и ограничения без чтения всей реализации.

#### Scenario: Добавляется новая экспортируемая функция
- **WHEN** разработчик добавляет новую экспортируемую функцию в TypeScript-модуль
- **THEN** рядом с функцией присутствует комментарий с целью, входами/выходами и значимыми побочными эффектами
- **AND** комментарий объясняет намерение, а не дублирует очевидный синтаксис

#### Scenario: Добавляется новый экспортируемый тип или константа
- **WHEN** разработчик добавляет экспортируемый тип или константу
- **THEN** рядом присутствует комментарий, объясняющий назначение и контекст использования
- **AND** для доменных констант зафиксированы допустимые значения или ограничения

#### Scenario: Создаётся нетривиальный файл
- **WHEN** разработчик создаёт файл с несколькими логическими блоками или неочевидными допущениями
- **THEN** в начале файла присутствует краткий комментарий о роли файла и границах ответственности

### Requirement: Именование и литералы остаются самодокументируемыми
Система разработки SHALL требовать осмысленные имена сущностей и исключать неочевидные сокращения и магические литералы в бизнес-логике.

#### Scenario: В код добавляется новое имя функции или переменной
- **WHEN** разработчик вводит имя новой сущности
- **THEN** имя отражает действие или доменный смысл
- **AND** не используются сокращения, которые нельзя однозначно понять без внешнего контекста

#### Scenario: В бизнес-логику добавляется литерал
- **WHEN** в коде появляется строковый или числовой литерал, влияющий на поведение
- **THEN** литерал вынесен в именованную константу или enum
- **AND** назначение значения объяснено через имя и, при необходимости, комментарий

#### Scenario: Значение имеет физическую или техническую единицу
- **WHEN** в коде задается значение времени, размера, количества или длительности
- **THEN** имя содержит единицу измерения (`Ms`, `Sec`, `Bytes`, `Count`, `Percent`)
- **AND** исключается двусмысленность интерпретации значения

### Requirement: Сложность кода контролируется в изменяемых модулях
Система разработки SHALL требовать, чтобы изменяемые модули сохраняли читаемую структуру: одна функция решает одну задачу, ветвления и вложенность остаются в пределах командного guidance.

#### Scenario: Функция в PR становится перегруженной
- **WHEN** функция в рамках изменения содержит смешанные ответственности или чрезмерную вложенность
- **THEN** функция разделяется на более простые части с осмысленными именами
- **AND** ключевой поток выполнения остаётся линейно читаемым

#### Scenario: В PR добавляется сложная логика с исключениями
- **WHEN** логика требует нескольких веток с особыми условиями
- **THEN** пограничные случаи оформляются явно (guard clauses или выделенные helpers)
- **AND** комментарии фиксируют бизнес-мотивацию нетривиальных веток

### Requirement: Размер файлов и функций ограничен стандартными soft-limit
Система разработки SHALL применять явные soft-limit для размера изменяемых файлов и функций, чтобы код сохранял локальную читаемость и предсказуемость ревью.

#### Scenario: Изменяемый production-файл превышает размер
- **WHEN** в PR изменяемый `*.ts` или `*.tsx` production-файл превышает 300 строк кода (без пустых строк и комментариев)
- **THEN** разработчик обязан разделить файл на логические модули
- **AND** если разделение в этом PR невозможно, добавляется документированное временное исключение с причиной, владельцем и `targetStage` закрытия

#### Scenario: Изменяемый test/storybook-файл превышает размер
- **WHEN** в PR изменяемый test/storybook-файл превышает 450 строк кода (без пустых строк и комментариев)
- **THEN** разработчик обязан вынести повторяющиеся блоки в helpers/fixtures
- **AND** структура файла должна сохранять быстрый поиск сценариев и ожиданий

#### Scenario: Функция превышает soft-limit
- **WHEN** функция в изменяемом модуле превышает 60 строк кода (без пустых строк и комментариев)
- **THEN** функция декомпозируется на подфункции с явными именами и ответственностями
- **AND** ключевой сценарий остаётся читаемым сверху вниз без скрытых побочных эффектов

### Requirement: Контракты ошибок и nullability явно определены
Система разработки SHALL требовать единый типизированный контракт ошибок и явное управление nullable-значениями на границах модулей.

#### Scenario: Функция возвращает ошибку в доменной логике
- **WHEN** функция сигнализирует о неуспехе
- **THEN** используется типизированный контракт ошибки, согласованный в проекте
- **AND** не используются разнородные и неструктурированные формы ошибок для одного и того же слоя

#### Scenario: На вход модуля приходит nullable-значение
- **WHEN** boundary-функция получает потенциально `null` или `undefined` данные
- **THEN** проверка и нормализация выполняются на границе модуля
- **AND** внутренняя логика модуля работает с предсказуемыми типами без скрытых nullable-веток

### Requirement: Публичные API избегают boolean-trap аргументов
Система разработки SHALL запрещать boolean-trap параметры в публичных и доменных функциях, если флаг влияет на альтернативные ветки поведения.

#### Scenario: В экспортируемую функцию предлагается добавить флаг
- **WHEN** параметр типа `boolean` используется для переключения режима поведения
- **THEN** функция принимает именованный объект параметров или разделяется на явные функции
- **AND** вызов читается без необходимости расшифровывать позиционные `true/false`

### Requirement: Сайд-эффекты изолированы от доменной логики
Система разработки SHALL изолировать I/O, env, время, сеть и другие сайд-эффекты в адаптерах, сохраняя доменную логику максимально чистой.

#### Scenario: Реализуется бизнес-правило, требующее внешнего доступа
- **WHEN** для вычисления результата нужно читать env, сеть, файловую систему или текущее время
- **THEN** внешние операции инкапсулируются в адаптере
- **AND** доменная функция получает необходимые данные через явный интерфейс зависимости

### Requirement: Асинхронный код безопасен и предсказуем
Система разработки SHALL запрещать floating promises и требовать явную обработку ошибок в асинхронных потоках.

#### Scenario: В модуле запускается асинхронная операция
- **WHEN** создается `Promise` в рамках бизнес- или прикладной логики
- **THEN** операция либо ожидается (`await`), либо явно управляется и документируется как фоновая
- **AND** путь обработки ошибок определен и проверяем

### Requirement: Нетривиальные API имеют usage-примеры
Система разработки SHALL требовать короткие usage-примеры для экспортируемых API со сложным или неочевидным контрактом.

#### Scenario: Добавляется нетривиальный экспортируемый API
- **WHEN** функция, тип или константа имеет нетривиальные предпосылки/ограничения
- **THEN** рядом добавляется короткий пример корректного использования
- **AND** пример покрывает основной happy-path и ключевое ограничение контракта

### Requirement: TODO/FIXME и deprecation оформляются управляемо
Система разработки SHALL требовать, чтобы временные пометки и обратная совместимость имели владельца и план закрытия.

#### Scenario: В код добавляется `TODO` или `FIXME`
- **WHEN** разработчик оставляет временную пометку
- **THEN** пометка содержит владельца и целевой этап/дату закрытия
- **AND** бесконтекстные `TODO/FIXME` без плана не допускаются

#### Scenario: Переименование или удаление публичной сущности
- **WHEN** меняется публичный контракт модуля или API
- **THEN** фиксируется deprecation-путь, период совместимости и критерий удаления legacy-пути
- **AND** документация и traceability отражают этот переход

### Requirement: Практики читаемости проверяются через единый тестовый слой
Система разработки SHALL проверять соблюдение capability `code-readability` через общий слой тестирования и traceability, а временные исключения фиксировать в coverage-plan с этапом закрытия.

#### Scenario: Разработчик запускает обязательные проверки change
- **WHEN** разработчик запускает `npm run test:unit` и `npm run test:traceability`
- **THEN** проверяется связь тестов/правил с capability `code-readability` и его scenario
- **AND** результат проверки однозначно показывает, соблюдён ли минимальный контракт читаемости

#### Scenario: Часть сценариев временно не автоматизирована
- **WHEN** для отдельного сценария capability `code-readability` ещё нет автоматической проверки
- **THEN** в `test/traceability/coverage-plan.json` добавлена запись с причиной и `targetStage`
- **AND** запись содержит конкретный план закрытия технического долга
