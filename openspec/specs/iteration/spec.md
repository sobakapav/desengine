# Итерация (LLM-запуск)

Итерация — основной цикл работы пользователя над проектом через workflow.

## Purpose

Определить контракт одного workflow-действия с LLM: что считается входом, что считается результатом и как система ведёт себя при ошибках.

## Requirements

### Requirement: Workflow action использует обязательные входные данные

Система SHALL включать в каждую итерацию:
- активный проект;
- активный компонент проекта, если он выбран;
- текущий `workflowStep`;
- пользовательский prompt;
- все рабочие файлы, разрешённые на текущем шаге;
- все изображения и другие артефакты, разрешённые текущему шагу;
- системные prompt-инструкции;
- явный список файлов, которые разрешено вернуть как результат.

Текущий prompt пользователя SHALL входить в PromptContext как `userText`.

#### Scenario: Пользователь запускает уточняющий prompt
- **WHEN** пользователь запускает итерацию
- **THEN** система включает в контекст проекта рабочие файлы и артефакты текущего шага
- **AND** строит PromptContext через общий builder
- **AND** PromptContext содержит пользовательский prompt в `userText`

#### Scenario: Система собирает текст итерационного prompt
- **WHEN** система формирует итоговый prompt для `iterate`
- **THEN** она явно перечисляет разрешённые файлы результата текущего шага
- **AND** использует `userText` из PromptContext

### Requirement: Workflow start использует обязательный контекст текущего шага

Система SHALL выполнять инициирующий запуск workflow step только с тем контекстом, который нужен для генерации рабочего набора файлов и артефактов текущего шага.

#### Scenario: Система инициирует workflow step
- **WHEN** пользователь впервые входит в активный workflow step
- **THEN** система отправляет разрешённые артефакты шага
- **AND** не отправляет фиктивное текущее состояние файлов, которые ещё не были созданы
- **AND** использует системные prompt-инструкции этого шага

#### Scenario: Система собирает текст инициирующего prompt
- **WHEN** система формирует итоговый prompt для `start`
- **THEN** она явно перечисляет разрешённые файлы результата текущего шага

### Requirement: Итерация возвращает обновлённые версии файлов

Система SHALL возвращать результат итерации как обновлённые версии файлов набора проекта.

#### Scenario: Модель изменила только часть файлов
- **WHEN** итерация вернула изменения только для части файлов
- **THEN** остальные файлы остаются без изменений

### Requirement: No-op итерация не маскируется как успешное применение

Система SHALL отличать реальное применение изменений от `noop` результата, в котором ни один рабочий файл не изменился.

#### Scenario: Модель не изменила ни один рабочий файл
- **WHEN** итерация завершилась без изменений во всех разрешённых рабочих файлах
- **THEN** runtime возвращает отдельный результат `noop`
- **AND** UI не показывает сообщение об успешном применении
- **AND** система не записывает новый entry в историю уточнений

#### Scenario: Все изменения отфильтрованы allowlist текущего шага
- **WHEN** ответ модели затронул только файлы, недоступные на текущем шаге
- **THEN** runtime возвращает результат `noop`
- **AND** указывает причину `allowlist-filtered`

### Requirement: Ошибка итерации не разрушает текущее состояние проекта

Система SHALL сохранять текущее состояние проекта при ошибке LLM и позволять повторить действие.

#### Scenario: Провайдер вернул ошибку
- **WHEN** провайдер LLM вернул ошибку
- **THEN** система не теряет текущее состояние файлов
- **AND** показывает пользователю понятное сообщение

#### Scenario: Уточнение превысило bounded timeout
- **WHEN** пользователь запускает уточнение
- **AND** route или LLM-провайдер не отвечает за разумное время
- **THEN** composer выходит из состояния `Запуск…`
- **AND** система показывает retriable timeout-сообщение
- **AND** текст уточнения остаётся в поле для повторной отправки

#### Scenario: Workflow action получает bounded overload-отказ
- **WHEN** пользователь запускает workflow action
- **AND** runtime уже достиг bounded backlog budget
- **THEN** система показывает retriable overload-сообщение
- **AND** текущее состояние файлов и пользовательский текст сохраняются без частичных изменений

#### Scenario: Workflow action превышает runtime payload budget
- **WHEN** `start`, `iterate` или `check` получает oversized input, output или write-set
- **THEN** runtime возвращает bounded ошибку
- **AND** не меняет рабочие файлы и не пишет историю после отказа

### Requirement: История уточнений показывает учебный контекст итераций

Система SHALL хранить и показывать историю уточняющих запросов в порядке выполнения.

#### Scenario: Пользователь открывает историю уточнений
- **WHEN** у workflow есть несколько выполненных уточняющих запросов
- **THEN** система показывает их от первого к последнему
- **AND** для каждого запроса показывает время, текст, изменённые файлы и учебную стоимость
