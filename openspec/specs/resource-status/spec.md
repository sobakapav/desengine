# Статусы системных ресурсов

## Purpose

Зафиксировать контракт диагностики системных ресурсов: код определяет фактическое condition ресурса, а пользовательские тексты, инструкции и ссылки берутся из конфигурации ресурсов.

## Requirements

### Requirement: Системные статусы описываются как ресурсы

Система SHALL собирать карточки диагностики через единый механизм системных ресурсов, где каждый ресурс имеет стабильный `ResourceId`, итоговый `ResourceState`, summary, detail и опциональную инструкцию.

#### Scenario: Диагностика собирает ресурс через общий resolver

- **WHEN** код диагностики определил condition конкретного ресурса
- **THEN** система строит `Resource` через общий resolver ресурсов
- **AND** итоговый `Resource.state` берётся из конфигурации condition

#### Scenario: Новый ресурс должен быть описан в конфигурации

- **WHEN** в `RESOURCE_IDS` есть системный ресурс
- **THEN** для него существует описание в конфигурации ресурсов
- **AND** конфигурация содержит хотя бы один condition с итоговым `ResourceState`

### Requirement: Пользовательские тексты ресурсов вынесены из диагностического кода

Система SHALL хранить labels, summaries, details и инструкции системных ресурсов в конфигурационных файлах вне исполняемого кода диагностики.

#### Scenario: Диагностика выбирает текст по condition

- **WHEN** ресурс находится в конкретном condition
- **THEN** summary, detail и инструкция выбираются из конфигурации ресурсов
- **AND** диагностический код не содержит пользовательский текст этого condition

#### Scenario: Текст использует переменные шаблона

- **WHEN** конфигурационный текст содержит `{{variable}}`
- **THEN** resolver подставляет значение переменной из диагностического контекста ресурса

### Requirement: Описания ресурсов поддерживают ссылки

Система SHALL разрешать Markdown-ссылки в описаниях и инструкциях ресурсов, чтобы пользователь мог перейти к внутренним страницам или документации из текста статуса.

#### Scenario: Описание содержит внутреннюю ссылку

- **WHEN** detail ресурса содержит Markdown-ссылку
- **THEN** интерфейс показывает её как кликабельную ссылку
- **AND** остальной текст описания остаётся читаемым как обычный текст

### Requirement: Карточка ресурса может содержать контрол исправления

Система SHALL разрешать ресурсу объявить встроенный контрол исправления, когда конкретный неготовый статус можно исправить прямо из карточки.

#### Scenario: Карточка ресурса показывает встроенный контрол исправления

- **WHEN** ресурс находится в неготовом состоянии, которое можно исправить пользовательским действием
- **THEN** диагностика добавляет к ресурсу описание нужного контрола
- **AND** карточка ресурса показывает этот контрол под текстом статуса
- **AND** готовые или неисправимые из карточки состояния не показывают встроенный контрол

### Requirement: Система показывает актуальность собственного релиза

Система SHALL показывать собственную Git-версию как системный ресурс и сравнивать локальный релизный тег с последним доступным релизным тегом remote `origin`.

#### Scenario: Старая версия системы показывается предупреждением

- **WHEN** локальный релизный тег системы старше последнего релизного тега `origin`
- **THEN** ресурс версии системы получает состояние `warning`
- **AND** статус сообщает пользователю локальную и последнюю версии
- **AND** старая версия не блокирует доступ к системе
- **AND** карточка ресурса показывает действие `Обновить`, если рабочее дерево можно безопасно обновить

#### Scenario: Нерелизное Git-состояние не блокирует систему

- **WHEN** система запущена не из точного релизного тега
- **OR** система не может однозначно проверить remote-релизы и при этом не имеет точного релизного тега для текущего HEAD
- **THEN** ресурс версии системы объясняет Git-состояние как предупреждение
- **AND** доступ к системе не блокируется
- **AND** автоматическое обновление не выполняется поверх локальных изменений

#### Scenario: Локальные изменения поверх точного релизного тега не маскируют релизную версию

- **WHEN** система запущена из точного релизного тега
- **AND** рабочее дерево содержит локальные изменения
- **THEN** ресурс версии системы не показывает состояние development только из-за dirty worktree
- **AND** ресурс сохраняет релизную версию как актуальный локальный тег
- **AND** detail ресурса явно сообщает о наличии локальных изменений

#### Scenario: Недоступность remote-релизов не создаёт ложную тревогу при точном релизном теге

- **WHEN** система запущена из точного релизного тега
- **AND** система не может получить список релизных тегов remote `origin` (нет сети или origin недоступен)
- **THEN** ресурс версии системы не показывает предупреждение только из-за недоступности remote
- **AND** ресурс показывает локальный релизный тег как допустимое состояние

### Requirement: Проверка change включена в единый слой тестирования

Система SHALL покрывать resolver ресурсов unit-тестами и включать capability `resource-status` в traceability-слой.

Система SHALL запускать независимые diagnostics probes на auth/system path без последовательного ожидания и без потери стабильного порядка resource cards.

#### Scenario: Авторизация не ждёт sequential network probes диагностики

- **WHEN** система собирает `getResourceStates()` для `/auth` или `/system`
- **AND** LLM и allowlist resource probes независимы друг от друга
- **THEN** система запускает их параллельно
- **AND** не ждёт завершения первого probe перед стартом второго

#### Scenario: Параллельные probes не переставляют порядок resource cards

- **WHEN** система собирает `getResourceStates()` через параллельные diagnostics probes
- **THEN** итоговый порядок resource cards остаётся стабильным
- **AND** не зависит от того, какой probe завершился раньше

#### Scenario: Разработчик запускает unit-проверку статусов ресурсов

- **WHEN** разработчик запускает `npm run test:unit`
- **THEN** unit-тесты проверяют resolver ресурсов, подстановку переменных и полноту конфигурации

#### Scenario: Разработчик запускает traceability-проверку

- **WHEN** разработчик запускает `npm run test:traceability`
- **THEN** capability `resource-status` имеет тестовую привязку или план покрытия
