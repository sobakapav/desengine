Все работы в этом репозитории ведутся на русском языке: OpenSpec, документация, пользовательские тексты и комментарии в коде.

Любые изменения поведения системы нужно фиксировать в OpenSpec на русском языке:
- обновлять `openspec/specs/**`, если меняется действующий контракт;
- создавать новый change через `npm run openspec:new -- <name>`, если меняется или добавляется отдельная возможность.
- при создании change добавлять требования и задачи, обеспечивающие интеграцию тестирования этого change в единый слой тестирования системы (включая команды запуска, при необходимости credentials и mock-данные).

Тестовая часть behavior-change обязательна и должна быть понятной человеку:
- указать затронутые OpenSpec capability/scenarios;
- выбрать уровень проверки: static/contract, unit, component/browser, integration, e2e smoke или live/provider;
- указать команду запуска (`npm run test:unit`, `npm run test:e2e`, `npm run test:traceability`, `npm run test:full` и т.п.);
- описать mock/fixture-данные и live credentials, если они нужны;
- если покрытие откладывается, добавить запись в `test/traceability/coverage-plan.json` с причиной и этапом закрытия.

Если агент вносит изменения в систему, он не выполняет финальную проверку этих изменений самостоятельно. Такой агент может только сообщить агенту-родителю или пользователю, что реализация готова к внешней проверке. Финальную проверку, включая запуск тестов и любые формулировки вида `Прогнал тесты`, должен выполнять другой агент.

В этом репозитории `producer` считается полным owner change-линии:
- он одновременно отвечает за смысл, roadmap, диспетчеризацию и управленческую синхронизацию downstream changes;
- он работает источником истины для подчинённых changes;
- `dispatcher` считается дочерним change соответствующего `focus`, а не `producer`;
- `producer` и `dispatcher` в одной focus-линии находятся в конструктивной конкуренции: producer удерживает смысл и pressure на трансформацию, dispatcher удерживает тактический backlog и может спорить с producer по способу доставки;
- такая конкуренция считается полезным управленческим сигналом, а не ошибкой topology;
- наличие `dispatcher` не переносит полную ответственность с producer на другой change;
- на старте producer не обязан иметь формализованные требования и сценарии: они могут появляться как результат проработки roadmap, а не как входное условие создания producer.

Если для change нужна отдельная ветка, используй одну ветку формата `codex/<name-change>` и для проработки, и для реализации.

Без явного разрешения пользователя нельзя менять install-critical инфраструктуру: `Node.js`, сборщик, `Turbopack` и другие критичные для запуска части стека.
