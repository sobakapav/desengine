# Naming discipline для архитектурных changes

## Принцип

Имя крупной сущности должно сразу отвечать на вопрос "какую ответственность она держит в архитектуре". Если по имени нельзя отличить ownership-контуру от технического контейнера, naming discipline нарушена.

## Базовые правила

- Используй имя предметной или архитектурной ответственности, а не технического приёма реализации.
- Новое имя должно быть различимо от уже существующих крупных терминов в roadmap, dispatcher-line и коде.
- Если change меняет имя крупного модуля, он обязан объяснить, какую архитектурную путаницу устраняет новое название.
- Избегай анонимных контейнеров: `utils`, `helpers`, `common`, `misc`, `manager`, `bridge`, `engine` без уточняющего ownership-контекста.
- Не вводи новую "важную сущность" без явного места в коде и без связи с архитектурной картой.

## Когда naming становится routing-сигналом

Эскалируй change до `dispatcher-architecture` или прикладывай architectural evidence, если:

- появляется новый крупный термин для модуля, слоя, рабочего контура или взаимодействия;
- переименование меняет смысл ownership, а не только стилистику;
- несколько предметных линий используют одно и то же спорное имя для разных сущностей;
- старое имя скрывает архитектурную границу или смешивает несколько ответственностей в одном контейнере.

## Признаки хорошего имени

- По имени можно понять owner и главный тип ответственности.
- Имя помогает найти связанные файлы, документы и тесты.
- Имя не конфликтует с уже принятыми сущностями `Project`, `Task`, `Workflow`, `Workbench`, `LLM`, `код` и другими живыми терминами карты.
- Имя не обещает большего уровня абстракции, чем реально реализовано.

## Признаки плохого имени

- Имя описывает только форму кода: `store`, `service`, `handler`, `adapter` без предметного контекста.
- Имя превращает boundary-модуль в мусорный контейнер для разнородных зависимостей.
- Имя вводит новый синоним для уже существующей сущности без явной причины.
- Имя скрывает изменение ownership за локальной "технической" формулировкой.

## Минимум, который должен показать change

При изменении naming discipline downstream change должен явно указать:

1. Какое имя использовалось раньше и почему оно стало проблемой.
2. Какое имя предлагается теперь и какую ответственность оно отражает.
3. Где это имя будет жить в коде, документации и тестах.
4. Требует ли новое имя обновления boundary contract, ADR или routing playbook.
