# Словарь архитектурных сущностей

## Как пользоваться словарём

Словарь нужен для двух задач:

- одинаково называть важные сущности в OpenSpec, коде и документации;
- быстро проверять, не пытается ли новый change тайно ввести новую архитектурную модель.

Если change вводит новую важную сущность, он должен:

1. добавить её в этот словарь;
2. обновить [карту архитектуры](./map.md);
3. при изменении управленческого правила добавить или обновить ADR.

## Основные сущности

### `Project`

Пользовательский scope работы, внутри которого живут настройки, артефакты и дальнейшие сущности выполнения.

Текущий кодовый контур:

- `lib/project/**`

Инварианты:

- `Project` не является просто глобальным env-набором;
- project-level контракт должен быть доступен downstream сущностям явно.

### `Task`

Пользовательская задача, которую система помогает выполнить.

Текущий кодовый контур:

- `lib/task/**`
- `onboarding/tasks/**`

Инварианты:

- task-level lab flow считается текущим рабочим профилем системы;
- `Task` не должен навсегда оставаться равным только component-level учебному сценарию.

### `WorkflowInstance`

Экземпляр процесса выполнения задачи, который связывает шаги, артефакты и рабочие поверхности.

Инварианты:

- workflow не подменяется списком UI-переходов;
- один workflow может включать несколько шагов и несколько workbench-состояний.

### `WorkflowStep`

Шаг workflow, в рамках которого открывается конкретный рабочий контекст.

Инварианты:

- шаг не обязан иметь жёсткое отношение `1:1` с верстаком;
- шаг должен быть достаточно явным, чтобы на него можно было привязать prompt context, артефакты и события.

### `WorkbenchDefinition`

Описание типа рабочего места: какие инструменты, layout и правила оно поддерживает.

Инварианты:

- это не текущий React-компонент, а архитектурный контракт профиля рабочего места;
- разные виды workbench должны выражаться через общий контракт, а не через параллельные самодельные registry.

### `WorkbenchInstance`

Конкретное состояние рабочего места, связанное с project/task/workflow step.

Текущий кодовый контур:

- `components/desengine/lab/Workbench/**`

Инварианты:

- instance хранит состояние и bindings, а не только визуальный layout;
- текущий lab workbench является первым instance/profile, но не единственным допустимым.

### `WorkbenchTool`

Отдельный инструмент внутри рабочего места.

Примеры:

- редактор кода;
- preview;
- инспектор изображений;
- prompt composer.

Инварианты:

- tool должен иметь явную applicability и state boundary;
- новые инструменты не должны обходить общий workbench contract.

### `Artifact`

Входной или выходной материал работы, который участвует в task/workflow/workbench контуре.

Примеры:

- изображение-референс;
- кодовый файл;
- prompt/history entry;
- check-result;
- импортированный дизайн-ресурс.

Инварианты:

- артефакт должен быть привязан к контексту использования;
- `Artifact` не сводится только к файлам на диске.

### `PromptContext`

Нормализованный контекст, который получает prompt/LLM слой.

Содержит:

- project;
- task;
- workflow step;
- workbench state;
- artifacts;
- пользовательский ввод;
- ограничения и runtime capabilities.

Инварианты:

- контекст должен быть общим между task hints, prompt builder и runtime services;
- route handlers не должны собирать несовместимые версии контекста по месту.

### `ApplicationService`

Оркестратор пользовательского flow, отделённый от route handler и UI.

Текущий кодовый контур:

- `lib/task/actions/**`

Инварианты:

- service отвечает за orchestration, а не за transport;
- route handler должен только валидировать вход, вызывать service и маппить ответ.

### `StorageAdapter`

Явная граница доступа к данным и файловому хранилищу.

Инварианты:

- прямые `fs`-операции не должны бесконтрольно расползаться по системе;
- смена storage или упаковка в другую среду проходит через adapter boundary.

### `EventEnvelope`

Общий контейнер для событийных слоёв.

Связанный документ:

- `docs/event-envelope-mvp.md`

Инварианты:

- experience/cost/log события могут иметь разный payload;
- scoping, privacy и lifecycle должны быть совместимы.

### `Dispatcher`

Тактический owner change-линии, который удерживает operational backlog и маршрутизирует downstream changes.

Инварианты:

- dispatcher не подменяет producer;
- dispatcher не должен становиться свалкой всех тем сразу.

### `Producer`

Полный owner change-линии, который отвечает за смысл, roadmap и управленческую синхронизацию.

Инварианты:

- producer держит стратегическую рамку;
- producer может делегировать тактическое исполнение, но не ответственность за общую картину.

## Сквозные сущности

### `код`

Сквозной архитектурный контур, который должен иметь явные модули, contracts и naming discipline.

### `LLM`

Сквозной контур генерации и интерпретации, который не должен растворяться в route handlers и prompt-строках.

### `бюджет`

Сквозной контур стоимости, лимитов и cost-сигналов. Он важен как сущность, но не является отдельным слоем UI сам по себе.

### `дизайн`

Сквозной контур дизайн-ресурсов и связанного рабочего материала. Он может опираться на Figma и импортируемые артефакты, но не сводится к одному внешнему инструменту.

## Намеренно исключённые или невыделенные элементы

### `AI-трансформация`

Это стратегическая рамка producer-линии, а не operational-сущность, которую нужно искать как модуль в коде.

### `сессия работы`

Пока не выделяется в отдельный слой. Если позже появится отдельный lifecycle и самостоятельные границы, сущность нужно будет формализовать отдельно.

### `документация`

Остаётся governance-опорой и внешним рабочим материалом, но не вводится как сквозная продуктовая сущность.

### `Figma`

Остаётся важной внешней средой дизайна, но не становится внутренней архитектурной сущностью сама по себе.
