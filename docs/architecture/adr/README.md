# ADR-реестр и правила

## Назначение

Этот каталог хранит архитектурные решения, которые уже должны направлять downstream changes. ADR в этом репозитории нужны не для исторического архива ради архива, а для фиксации правил, по которым команда:

- понимает, какая архитектурная ставка уже принята;
- отличает локальный refactor от изменения архитектурной границы;
- решает, когда нужно обновлять карту архитектуры и словарь сущностей.

Тактический owner этого контура: `dispatcher-architecture`.

## Когда нужен новый ADR

Создавай новый ADR, если change:

- вводит новую важную сущность или меняет её статус;
- меняет слой, ownership или boundary крупной части системы;
- задаёт новое правило для маршрутизации downstream changes;
- отменяет или ограничивает прежнее архитектурное решение;
- фиксирует guardrail, без которого следующие changes начнут расходиться.

Не нужен новый ADR, если change:

- делает локальный refactor внутри уже принятой границы;
- исправляет баг без изменения архитектурного правила;
- просто синхронизирует документацию с уже принятым ADR.

## Формат и жизненный цикл

Имя файла:

- `ADR-XXXX-короткое-имя.md`

Статусы:

- `proposed` — решение обсуждается и ещё не является обязательным источником истины;
- `accepted` — решение обязательно для downstream changes;
- `superseded` — решение заменено более новым ADR;
- `deprecated` — решение больше не должно расширяться, но пока ещё важно для чтения истории.

Каждый ADR должен содержать:

- статус;
- контекст;
- решение;
- последствия;
- ссылки на связанные документы и changes.

## Обязательная синхронизация

Если ADR со статусом `accepted` меняет архитектурную картину, change обязан одновременно:

1. обновить [карту архитектуры](../map.md);
2. обновить [словарь сущностей](../glossary.md), если меняется состав или смысл сущностей;
3. сослаться на ADR в собственных OpenSpec-артефактах, если change дальше делегирует тему downstream.
