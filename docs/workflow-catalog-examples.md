# Workflow Catalog Examples

Этот файл фиксирует примеры workflow, которые продукт должен уметь поддерживать как операции над проектом, компонентами, экранами, данными и системой в целом.

## Исходный список примеров

1. Создание простого React-компонента по его картинке или Figma-коду (JSON).
2. Сборка сложносоставного React-компонента из нескольких простых.
3. Вычленение структуры и базовой реализации React-компонентов из вайбкодинг-прототипа системы.
4. Проработка карты (дерева) React-компонентов и экранов.
5. Композиционная проработка экранов.
6. Переключение проекта с одной дизайн-системы на другую или с одного UI-кита на другой.
7. Генерация mock-данных для проработки дизайна на граничных условиях.
8. Создание Storybook-слоя проекта.
9. Интеграция имеющейся системы React-компонентов проекта с имеющимся во внешнем проекте Storybook-слоем.
10. Создание выкрасок — страниц с наглядной демонстрацией React-компонентов и их поведения.
11. Видеоэкспорт демок поведения React-компонентов.
12. Документирование React-компонентов.
13. Загрузка в проект Figma-проекта и разбиение его на React-компоненты и экраны.
14. Адаптация стилевого решения проекта по визуальным референсам.
15. Генерация диаграмм, объясняющих структуру проекта.
16. Общий автоматический рефакторинг системы React-компонентов — выявление шаблонов и т.п.
17. Работа с доменной моделью данных.
18. Параметризация дизайна, выявление точек такой параметризации, вынос в пропсы.
19. Раскладывание текстового сценария на последовательность интерфейсов с данными.
20. Нюансировка интерактива и состояний React-компонента.
21. Организация фабрики примеров и моков данных.
22. Эмуляция задержек при отрисовке интерфейса и проработка состояний постепенного прогружения компонента и экрана.
23. Организация массового производства React-компонента через `map` и подобные функции.

## Что видно по этим примерам

Список уже показывает, что `workflow` не может оставаться только:

- проектным readout;
- линейным recipe вокруг одного компонента;
- жёстко зашитым в один `workflowKind`;
- привязанным только к коду компонента без данных, экранов и доменной модели.

Нужна модель, в которой workflow является каталогом проектных операций.

## Основные семейства workflow

### 1. Component Creation

- создать простой компонент из изображения или Figma JSON;
- собрать сложный компонент из простых;
- адаптировать стиль по референсам;
- вынести параметры в пропсы;
- доработать состояния и интерактив;
- организовать массовое производство компонентов.

### 2. Screen Composition

- собрать дерево компонентов и экранов;
- композиционно проработать экран;
- разложить текстовый сценарий на последовательность интерфейсов;
- подготовить выкраски и демонстрационные страницы.

### 3. System Extraction And Refactoring

- выделить структуру компонентов из вайбкодинг-прототипа;
- провести migration между UI kit или дизайн-системами;
- выявить шаблоны и провести системный рефакторинг.

### 4. Data And Domain

- генерировать граничные mock-данные;
- строить фабрику моков и примеров;
- прорабатывать доменную модель данных;
- моделировать загрузку и задержки, чтобы работать с реальными состояниями интерфейса.

### 5. Storybook And Documentation

- создать Storybook-слой;
- интегрировать проектный компонентный слой с внешним Storybook;
- документировать компоненты;
- готовить видеоэкспорт поведения компонентов.

### 6. Import And Analysis

- загрузить Figma-проект и разложить его на экраны и компоненты;
- строить диаграммы структуры проекта.

## Какие измерения должна уметь описывать архитектура workflow

### Subject kind

Workflow должен уметь работать не только с `component`, но и с:

- `project`;
- `component-set`;
- `screen`;
- `screen-set`;
- `data-set`;
- `domain-model`;
- `storybook-layer`;
- `prototype`;
- `reference-pack`;
- `design-system-migration`.

### Operation family

Каждый workflow должен принадлежать к понятному семейству операций:

- `create`;
- `compose`;
- `extract`;
- `map`;
- `integrate`;
- `migrate`;
- `generate`;
- `document`;
- `refactor`;
- `simulate`;
- `present`.

### Inputs

Workflow должен явно требовать входы, а не неявно ждать их наличия:

- изображение;
- Figma JSON;
- Figma project import;
- набор существующих компонентов;
- кодовая база проекта;
- текстовый сценарий;
- визуальные референсы;
- доменная схема;
- данные и mock-фабрики;
- Storybook-слой.

### Outputs

Workflow должен объявлять ожидаемые результаты через artifacts:

- React-компоненты;
- экраны;
- карты структуры;
- mock-данные;
- Storybook stories;
- documentation artifacts;
- demo pages;
- video assets;
- migration plans;
- diagrams;
- parameter contracts.

## Следствие для архитектуры

Если workflow должен покрывать такой каталог, то он не может оставаться только “набором project stages”.

Минимально нужна трёхслойная модель:

1. `WorkflowDefinition` как шаблон операции.
2. `WorkflowRun` как запуск этой операции в контексте конкретного проекта.
3. `WorkflowSubject` как явное указание, над чем именно идёт работа.

Именно этот вывод дальше закрепляется в OpenSpec change `implement-workflow-project-recipe-definitions-subject-scopes-artifacts-inputs`.
